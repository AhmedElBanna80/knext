In-process Rust (Beta): the module `knext ffi generate` writes now refuses to load a Rust library that anyone but root can change after its sha256 was checked. A checksum covers the bytes read at that moment, and an open file pins the file, not its contents, so an in-place write by someone else would still have changed what runs. Root must own the library, every directory from it up to `native/`, and the directory `native/` sits in, and none of them may be writable by its group or by everyone; the module checks that by owner and mode. A tree owned by anyone else is refused with an `FfiLoadError` that names the path and the fix, the user the app runs as included: it could change the permissions of what it owns and write the library again. The image `knext build` generates already copies `native/` owned by root and read-only (`COPY --chown=0:0 --chmod=a-w`), so it loads as before. If you write your own Dockerfile, copy `native/` the same way, run the app as a non-root user, and keep the directory that holds `native/` owned by root and not writable by group or other (a `chown` of the app directory to the app user now fails the check); a volume mounted at `native/` that a sidecar or an `fsGroup` can write is refused too. There is no opt-out. Root is not stopped, and neither is a second writable mount of the same files or an access control list that grants write: a process running as root, or one allowed to bypass file permissions, can still change the library. Regenerate your wrapper with `knext ffi generate`; `knext ffi check` reports the committed one as out of date until you do.
