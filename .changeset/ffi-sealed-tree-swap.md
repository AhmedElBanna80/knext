In-process Rust (Beta): the module that `knext ffi generate` writes now refuses to load a Rust library unless no user but root could have swapped the tree it is read from. Regenerate your wrapper with `knext ffi generate`; `knext ffi check` reports the committed one as out of date until you do, and a wrapper generated before this change keeps the old loader and is not protected until you regenerate it.

- Why: the module used to look at the integrity manifest, the library and their directories one after the other by path. Someone who could write a directory above the one that holds your executable could rename the whole tree away for a moment and put their own manifest and a link to any library root owns in its place; the real tree came back before the directories were looked at, and every check passed.
- What it requires: root owns every directory from the library up to `/` (below `native/`, `native/` itself, the directory beside your executable and each directory above it) and none of them is writable by group or other, so a user who is not root cannot rename any of them. The same goes for `native/.integrity.json`, as it already did for the library.
- What it never does: follow a symbolic link at the manifest, the library or any directory inside the tree (a link is refused, whatever it points at), or wait on a pipe. It reads only plain files and looks at the directories and files again after the library is hashed.
- Images knext builds: the Dockerfile that `knext build`, `knext deploy` and `knext preview` stage already passes. With `knext.ffi.json`, its standalone version gains one `RUN chmod go-w` line that closes `native/` and the directories above the executable, which a monorepo layout would otherwise inherit from the build host (group-writable under a umask of 002).
- vinext apps: the vinext template is the app's own scaffolded `Dockerfile` and is not changed. `knext ffi init`, `knext ffi generate` and `knext ffi check` print the line to add, `RUN chmod go-w /app /app/native`, to go directly after the `COPY` that brings `native/` in, and nothing else in the file needs to change. `knext deploy` still recognises the scaffolded file with just that line, so the app keeps its build and asset upload. When both directories are closed but not by that one line directly after the `COPY`, they warn that `knext deploy` takes the slower path; an app built with another builder is told none of this (those builds stage a `Dockerfile` that already has the line), and one whose build cannot be read is told as if it were vinext. Under BuildKit nothing changes for an existing app; with another builder the first call is refused, and the message says how to fix the directories (a closing `chmod` anywhere else also closes them, but takes `knext deploy` to the slower path). The hint reads your `RUN`s the way a shell does (quoted words, `/bin/chmod`, `sudo`, a path with a dot in it, the `WORKDIR`, the exec form, `sh -c`, `cd`, `find -exec`, a heredoc body), and what it cannot read it counts as opening the directories, never as closing them: when a `RUN` after the `COPY` opens them (or may), it says so and where to close them again, instead of asking for a line that would not help.
- Where the executable is judged: Bun reports `process.execPath` already resolved, so an install reached through a link (a `current -> releases/12` link, `/var`, a merged `/usr`) loads, and the directories judged are those of the real tree. The module still refuses a path that is not its own real path, as a fail-closed assertion that Bun does not trigger.
- Capistrano and its relatives: a deploy tool that keeps releases in a directory it owns is refused by the ownership rule, not for its link. Put `deploy_to` under a parent where every directory from that parent up to `/` is root-owned and closed to group and other, make `deploy_to`, `releases/` and each release root-owned and closed to group and other, and never change anything above `deploy_to`. Switching `current` and `deploy:cleanup` need root too, as does the step that puts the files in place.
- The refusal message: every failing directory is listed at once, and the advice follows the situation. A directory inside `native/` is fixed in place (`chmod go-w`, `chown root`). A sticky directory (a shared one such as `/tmp`) at or above the executable is only told to move the install under a root-owned, closed directory such as `/opt/<app>`. Any other failing directory (the executable's own, or one above it, a world-writable one included) is told both, each with its condition, and that the executable needs a directory of its own; a home directory is told to move the install, never to be given to root. Where `/app` or `/app/native` is on the list and can be fixed in place, the message also names the one Dockerfile line that keeps a vinext app on the known-good path (that line closes those two and no other), and with a sticky directory on the list together with others it says that fixing the others alone will not be enough. On some hosts `/opt` itself is writable by everyone and is then named in the refusal: pick another parent that root owns and closes, such as `/var/lib`.
- Names in messages: a link or a regular file where a directory belongs is named as such. Every path, system error and value read from a file or the environment that a refusal prints is shown escaped: C0 controls and DEL in caret notation (a newline is `^J`), and C1 controls, the line and paragraph separators, every Unicode format character (the bidirectional controls, the zero-width characters, the soft hyphen, the invisible operators, the tag characters), the combining grapheme joiner and a lone surrogate (a half of a pair, which a JSON string in the manifest can hold) as `\u` escapes, so none reaches your terminal or log as itself, and a backslash or caret is escaped so that a name that really holds an escape is not mistaken for one; invalid UTF-8 in a file name or an environment value is shown as U+FFFD. The error text your Rust code returns is not touched: it reaches `RustError.message` as the code wrote it. A digest the manifest lists that is not 64 lowercase hexadecimal digits is refused, with that said.
- Your own image: copy `native/` as plain files with `COPY --chown=0:0 --chmod=a-w`, add `RUN chmod go-w /app /app/native` after it so the result does not depend on the mode your builder gives a copy's destination, do not hand any directory above it to the app user or make it group- or world-writable, and after a `COPY . /app` run `chmod -R go-w /app` (the directories inside a copied tree keep the build machine's mode).
- A binary you run outside a container: it is refused when a directory above it is not root's. One under a root-owned `/opt/<app>` is fine, and so is `/usr/local` where root owns it and group and other cannot write it (Homebrew on Intel macOS gives it to your user, and some Debian systems ship it `root:staff` with mode 2775, so check); one under a home directory or `/tmp` is not. The commands the page gives for handing the directory to root (`chown -R`, so they change everything in it) check it first and change nothing unless it is exactly an app: they follow a link to the real directory, which must hold `native/` (with its `.integrity.json`) and one other entry, your executable as a regular file, and nothing else, and must not be a system, home or temporary directory (`/`, `/opt` itself, `/tmp`, `/var/lib`, `/dev`, `/run`, `/etc`, a home directory or anything under one, and the like); a path that is not absolute, does not exist, or fails either check is refused with the reason. `/opt/<app>` and `/usr/local/<app>` pass.
- Volumes: a volume shared with a sidecar or writable through an `fsGroup` is refused unless root owns everything on it and group and other cannot write it, and one that passes is still writable through its other mounts.
- What it does not stop: code running as root or with any capability that is equivalent to root, for example `CAP_DAC_OVERRIDE`, `CAP_FOWNER`, `CAP_CHOWN`, `CAP_SETUID`, `CAP_SYS_ADMIN`, `CAP_SYS_PTRACE`, `CAP_MKNOD`, `CAP_SYS_MODULE`, `CAP_SYS_RAWIO` or `CAP_BPF`; a second writable mount of the same files; an ACL that grants write; a seekable file write as the app's user through `/proc/self/mem`.
- Running as non-root: the knext operator's pods drop every capability, set `allowPrivilegeEscalation: false` and run as non-root unless `spec.security.runAsNonRoot` says otherwise. Dropping capabilities is not enough for an app that runs as `uid 0`, which owns the tree, so run it as a non-root user too (`runAsNonRoot`), and add `--cap-drop=ALL --security-opt no-new-privileges --user 65532` to a container you run yourself.
- User namespaces are two cases: under rootless Podman or Docker the image's files belong to the host user who started the container, so running as a non-root user inside does not remove that writer. Under a pod with `hostUsers: false` the image's files belong to the pod's own root (host root where the filesystem supports idmapped mounts, otherwise the root of a uid range given to that pod alone, not host root), so no other user on the host can write them and running as a non-root user inside restores the guarantee.
