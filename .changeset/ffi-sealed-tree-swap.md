In-process Rust (Beta): the module that `knext ffi generate` writes now refuses to load a Rust library unless no user but root could have swapped the tree it is read from. The module used to look at the integrity manifest, the library and their directories one after the other by path, so someone who could write a directory above the one that holds your executable could rename the whole tree away for a moment and put their own manifest and a link to any library root owns in its place; the real tree came back before the directories were looked at, and every check passed. The module now requires root to own every directory from the library up to `/` (below `native/`, `native/` itself, the directory beside your executable and each directory above it) and to keep each from being written by group or other, so a user who is not root cannot rename any of them. It requires the same of `native/.integrity.json` as it already did of the library, never follows a symbolic link at the manifest, the library or any directory inside the tree (a link is refused, whatever it points at), reads only plain files without waiting on a pipe, and looks at the directories and files again after the library is hashed. The Dockerfile that `knext build`, `knext deploy` and `knext preview` stage already passes, and with `knext.ffi.json` its standalone version gains one `RUN chmod go-w` line that closes `native/` and the directories above the executable, which a monorepo layout would otherwise inherit from the build host (group-writable under a umask of 002); the vinext template is the app's own scaffolded `Dockerfile` and is not changed (every vinext app keeps its image), so for a vinext app `knext ffi init` prints the line to add, `RUN chmod go-w /app /app/native` after the `COPY` that brings `native/` in. The executable is judged where it really is: Bun reports `process.execPath` already resolved, so an install reached through a link (a `current -> releases/12` link, `/var`, a merged `/usr`) loads and the directories judged are those of the real tree; the module still refuses a path that is not its own real path, as a fail-closed assertion that Bun does not trigger. A deploy tool that keeps releases in a directory it owns (Capistrano and its relatives) is refused by the ownership rule, not for its link: put `deploy_to` under a parent that root owns and that is closed to group and other, make `deploy_to`, `releases/` and each release root-owned and closed to group and other (run the step that puts the files in place as root), and never change anything above `deploy_to`. When directories fail the check, the message lists every one of them, and the advice follows the situation: a directory inside `native/` is fixed in place (`chmod go-w`, `chown root`); a sticky or world-writable directory above the executable is shared with other software and is only told to move the install under a root-owned, closed directory such as `/opt/<app>`; any other failing directory (the executable's own, or one above it) is told both, each with its condition (part of your install: fix it in place; shared with other software: move the install instead), and that the executable needs a directory of its own (on some hosts `/opt` itself is writable by everyone and is then named in the refusal; pick another parent that root owns and closes, such as `/var/lib`). A link or a regular file where a directory belongs is named as such, and every path or system error a refusal prints is shown escaped (control characters, including the C1 controls and the line and paragraph separators, never reach your terminal or log). If you build your own image, copy `native/` as plain files with `COPY --chown=0:0 --chmod=a-w`, add `RUN chmod go-w /app /app/native` after it so the result does not depend on the mode your builder gives a copy's destination, do not hand any directory above it to the app user or make it group- or world-writable, and after a `COPY . /app` run `chmod -R go-w /app` (the directories inside a copied tree keep the build machine's mode). A compiled binary you run outside a container is refused when a directory above it is not root's: one under a root-owned `/opt/<app>` is fine, and so is `/usr/local` where root owns it and group and other cannot write it (Homebrew on Intel macOS gives it to your user, and some Debian systems ship it `root:staff` with mode 2775, so check), while one under a home directory or `/tmp` is not. A volume shared with a sidecar or writable through an `fsGroup` is refused unless root owns everything on it and group and other cannot write it, and one that passes is still writable through its other mounts. This does not stop code running as root or with any capability that is equivalent to root, for example `CAP_DAC_OVERRIDE`, `CAP_FOWNER`, `CAP_CHOWN`, `CAP_SETUID`, `CAP_SYS_ADMIN`, `CAP_SYS_PTRACE`, `CAP_MKNOD`, `CAP_SYS_MODULE`, `CAP_SYS_RAWIO` or `CAP_BPF`. The knext operator's pods drop every capability, set `allowPrivilegeEscalation: false` and run as non-root unless `spec.security.runAsNonRoot` says otherwise; dropping capabilities is not enough for an app that runs as `uid 0`, which owns the tree, so run it as a non-root user too (`runAsNonRoot`), and add `--cap-drop=ALL --security-opt no-new-privileges --user 65532` to a container you run yourself. Nor does it stop a second writable mount of the same files, an ACL that grants write, or a seekable file write as the app's user through `/proc/self/mem`. A user namespace is two cases: under rootless Podman or Docker the image's files belong to the host user who started the container, so running as a non-root user inside does not remove that writer, while under a pod with `hostUsers: false` the image's files belong to the pod's own root (host root where the filesystem supports idmapped mounts, otherwise the root of a uid range given to that pod alone, not host root), so no other user on the host can write them and running as a non-root user inside restores the guarantee. Regenerate your wrapper with `knext ffi generate`; `knext ffi check` reports the committed one as out of date until you do, and a wrapper generated before this change keeps the old loader and is not protected until you regenerate it.
