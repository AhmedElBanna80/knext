In-process Rust (Beta): the module that `knext ffi generate` writes now refuses to load a Rust library unless no user but root could have swapped the tree it is read from. The module used to look at the integrity manifest, the library and their directories one after the other by path, so someone who could write a directory above the one that holds your executable could rename the whole tree away for a moment and put their own manifest and a link to any library root owns in its place; the real tree came back before the directories were looked at, and every check passed. The module now requires root to own every directory from the library up to `/` (below `native/`, `native/` itself, the directory beside your executable and each directory above it) and to keep each from being written by group or other, so a user who is not root cannot rename any of them. It requires the same of `native/.integrity.json` as it already did of the library, never follows a symbolic link at the manifest, the library or any of those directories (a link is refused, whatever it points at), reads only plain files without waiting on a pipe, and looks at the directories and files again after the library is hashed. The image `knext build` generates already passes, and with `knext.ffi.json` its standalone Dockerfile gains one `RUN chmod go-w` line that closes the directories above the executable, which a monorepo layout would otherwise inherit from the build host (group-writable under a umask of 002). If you build your own image, copy `native/` as plain files with `COPY --chown=0:0 --chmod=a-w` and do not hand any directory above it to the app user or make it group- or world-writable. A compiled binary you run outside a container is refused when a directory above it is not root's: one under a root-owned `/opt/<app>` or `/usr/local` is fine, one under a home directory or `/tmp` is not. This does not stop code running as root (or with `CAP_DAC_OVERRIDE` or `CAP_FOWNER`), a second writable mount of the same files, or an ACL that grants write. Regenerate your wrapper with `knext ffi generate`; `knext ffi check` reports the committed one as out of date until you do, and a wrapper generated before this change keeps the old loader and is not protected until you regenerate it.
