In-process Rust (Beta): the module that `knext ffi generate` writes now refuses to load a Rust library unless no user but root could have swapped the tree it is read from. The module used to look at the integrity manifest, the library and their directories one after the other by path, so someone who could write a directory above the one that holds your executable could rename the whole tree away for a moment and put their own manifest and a link to any library root owns in its place; the real tree came back before the directories were looked at, and every check passed. The module now requires root to own every directory from the library up to `/` (below `native/`, `native/` itself, the directory beside your executable and each directory above it) and to keep each from being written by group or other, so a user who is not root cannot rename any of them. It requires the same of `native/.integrity.json` as it already did of the library, never follows a symbolic link at the manifest, the library or any of those directories (a link is refused, whatever it points at), reads only plain files without waiting on a pipe, and looks at the directories and files again after the library is hashed. The images `knext deploy` and `knext preview` build already pass, and with `knext.ffi.json` their standalone Dockerfile gains one `RUN chmod go-w` line that closes `native/` and the directories above the executable, which a monorepo layout would otherwise inherit from the build host (group-writable under a umask of 002). A link at or above the directory that holds your executable is refused too, before anything is read, and when directories fail the check the message lists every one of them with the fix for a directory. If you build your own image, copy `native/` as plain files with `COPY --chown=0:0 --chmod=a-w`, do not hand any directory above it to the app user or make it group- or world-writable, and after a `COPY . /app` run `chmod -R go-w /app` (the directories inside a copied tree keep the build machine's mode). A compiled binary you run outside a container is refused when a directory above it is not root's: one under a root-owned `/opt/<app>` is fine, and so is `/usr/local` where root owns it and group and other cannot write it (Homebrew on Intel macOS gives it to your user, and some Debian systems ship it `root:staff` with mode 2775, so check), while one under a home directory or `/tmp` is not. A volume shared with a sidecar or writable through an `fsGroup` is refused unless root owns everything on it and group and other cannot write it, and one that passes is still writable through its other mounts. This does not stop code running as root or with `CAP_DAC_OVERRIDE`, `CAP_FOWNER`, `CAP_CHOWN`, `CAP_SETUID`, `CAP_SYS_ADMIN`, `CAP_SYS_PTRACE` or `CAP_MKNOD` (the knext operator's pods drop every capability and set `allowPrivilegeEscalation: false`; add `--cap-drop=ALL --security-opt no-new-privileges` to a container you run yourself), a second writable mount of the same files, an ACL that grants write, a seekable file write as the app's user through `/proc/self/mem`, or an app that itself runs in a user namespace (rootless Podman or Docker, `hostUsers: false`), where `uid 0` is an unprivileged host user: run the app as a non-root user there too. Regenerate your wrapper with `knext ffi generate`; `knext ffi check` reports the committed one as out of date until you do, and a wrapper generated before this change keeps the old loader and is not protected until you regenerate it.
