A self-contained vinext build now carries the app's own data files inside the executable, so reads of them work from a directory that holds only the binary. That covers the files listed in `outputFileTracingIncludes` (minus `outputFileTracingExcludes`) and the project files the server code names by literal path, such as `join(process.cwd(), 'content/post.md')` or `new URL('../data.json', import.meta.url)`. They are read with `fs` or `fs/promises` by relative, working-directory or build-machine absolute path; the real disk wins when a file exists there, and any file that was not embedded is still a real `ENOENT`. The build fails instead of dropping an include that cannot be embedded: one that matches nothing, resolves outside the app root, is a dangling link or a special file, looks like a credential (judged by name, by where a symlink really points, and by directory; `.git` is never embedded), is a native addon, or belongs to a package the build traced into `.output/server/node_modules` (the executable cannot resolve a package from inside itself). A `next.config` that might declare includes is loaded in its own process as `next build` loads it (`NODE_ENV=production` when unset, the `.env` files `next build` loads, Next's `defaultConfig` for function configs); if it cannot be loaded, or a value is not a glob list, the build fails. Route keys of `outputFileTracingExcludes` are matched with the picomatch Next ships; without `next` installed, only an exact or all-routes key is applied and any other fails the build. The credential check matches names and is a safeguard, not a guarantee; an exact file path is the explicit opt-out.
