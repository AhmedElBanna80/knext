"@getknext/core": patch
---

`knext build`, `deploy` and `preview` now check `distDir`, `output: 'export'` and, on Bun with Turbopack, `experimental.turbopackModuleFragments` against the config Next.js resolved, not by reading `next.config` as text. Settings made by config wrappers, plugins or values computed from the environment are now judged correctly, both ways: a computed `distDir` that resolves to `.next` is no longer refused, and a wrapper that sets a custom `distDir` is no longer missed. With knext's adapter (the default for new apps) an unsupported setting is refused at the start of the build, before anything compiles. An app without knext's adapter is judged after its build, from the resolved config Next.js writes into its build directory (`.next`, or a custom top-level one such as `build`); nothing is added to its build. A nested custom `distDir` (such as `out/next`) on an app without the adapter is only caught by the text check. A plain `next build` you run yourself is not checked. When neither is available, the CLI warns and falls back to the earlier text check, after the build. Before the build, the text check also runs as an early warning. These still decide from the text alone: `knext build --skip-next`, the vinext build target, `knext doctor`, and the warned fallback when no resolved config is found. If the build script runs Next.js in a different directory than the one knext runs in, knext stops with an error naming it. The text check can be misled by a setting written inside a string, such as a comment-like string literal.
