<Callout type="warn">
**Beta, and not published yet.** In-process Rust runs **only on Bun**: it calls Rust through
`bun:ffi`, which Bun itself marks experimental ("Do not rely on it in production"). It is **not
covered by knext's compatibility credential**. The `knext ffi` commands come from the optional
`@getknext/ffi` package, which is not on npm yet: until it is installed in your app, `knext ffi`
prints how to install it and exits 1 (`--help` still exits 0). The Rust crates it needs are not on
crates.io either, so a zone depends on them by git commit from the knext repository.
</Callout>

A zone can ship **one** Rust library and call its functions from TypeScript **in the same
process**: no network hop and no extra cold start. You mark Rust functions with
`#[knext_ffi::export]`, run `knext ffi generate`, and get a typed, `server-only` TypeScript module
with one function per export. A Rust `String` comes back as a TypeScript `string`, a `Result::Err`
is thrown as a `RustError`, and a panic is thrown as a `RustPanicError` while the process keeps
running.

It is for hot, CPU-bound, stateless work measured in microseconds: parsing, validating, hashing,
transforming. For anything else, use a [zone function](/docs/cli#knext-add-function).

## When to use it, and when to use a zone function

| | In-process Rust | Zone function |
|---|---|---|
| Where it runs | inside the zone's own process | its own service, called over the network |
| Call cost | nanoseconds to microseconds (see [the measured costs](#blocking-and-workers)) | a network round trip, in milliseconds |
| Cold start | none of its own; the library loads on the first call | its own scale-from-zero |
| Scaling | scales with the zone | scales on its own, to zero |
| If it crashes | the whole zone pod restarts (an abort, a segfault, a stack overflow) | only the function's pod |
| Blocking | blocks the zone's JavaScript thread for the whole call | never blocks the zone |
| Languages | Rust | Go and Rust |
| Runtime | **Bun only** | Node and Bun |
| Security boundary | none: same process, same memory | separate process, authenticated, cluster-local |
| Use it for | short, CPU-bound, stateless functions | I/O, business logic, and anything that should scale, fail or deploy on its own |

## Quick start

### 1. Opt the zone in

```bash title="shell"
knext ffi init
```

This writes `knext.ffi.json` and a starter crate, and refuses to overwrite either if it exists:

```json title="knext.ffi.json"
{
  "version": 1,
  "crate": "rust",
  "out": "src/generated/ffi"
}
```

- `crate` is the Rust crate's directory and `out` is where the generated module goes. Both are
  relative to the app and must be a subdirectory of it: the app root itself, anything outside it,
  and anything under `node_modules` are refused. Unknown keys are refused too.
- `rust/Cargo.toml` builds a C-ABI library (`crate-type = ["cdylib"]`) and depends on `knext-ffi`
  by git, pinned to the full commit your installed `@getknext/ffi` records, so the Rust macros and
  the generator always agree. If the installed copy records no commit, `init` says so and writes
  nothing.
- `rust/rust-toolchain.toml` pins the Rust version and lists the two Linux targets images are built
  for.
- `rust/src/lib.rs` holds one function to start from:

```rust title="rust/src/lib.rs"
/// Says hello.
#[knext_ffi::export]
pub fn greet(name: &str) -> String {
    format!("Hello, {name}!")
}
```

### 2. Generate the TypeScript

Install Rust from [rustup.rs](https://rustup.rs), then:

```bash title="shell"
knext ffi generate
```

It builds the crate for your machine (`cargo build --release`), reads the list of exported functions
from the built library itself, and writes `src/generated/ffi/index.ts` plus
`src/generated/ffi/.knext-generated.json`, the record of what it wrote. **Commit both, and commit
`rust/Cargo.lock`**: image builds use the lockfile as it is. The generated module is committed so
that `next build` and type-checking work on a fresh checkout with no Rust installed.

`knext ffi check` does the same build and fails if the committed module is out of date; run it in
CI. It compares bytes, so keep the output directory out of your formatter and linter.

### 3. Call it from a Server Action

```ts title="src/app/actions.ts"
'use server';

import { greet } from '../generated/ffi';

export async function sayHello(name: string): Promise<string> {
  return greet(name);
}
```

```tsx title="src/app/page.tsx"
'use client';

import { useState } from 'react';
import { sayHello } from './actions';

export default function Page() {
  const [message, setMessage] = useState('');
  return (
    <main>
      <button type="button" onClick={async () => setMessage(await sayHello('World'))}>
        Say hello
      </button>
      <p>{message}</p>
    </main>
  );
}
```

The generated module starts with `import 'server-only'`, so importing it into a Client Component
fails the build. Route handlers and dynamically rendered pages can call it too (see
[Dynamic contexts only](#dynamic-contexts-only)).

### 4. Run it

```bash title="shell"
bun --bun next dev
```

In development the module loads the library `knext ffi generate` just built, from
`rust/target/release/` (or `rust/target/debug/`, whichever is newer), and prints one line saying it
skipped the integrity check:

```
knext ffi: loading the development build …/rust/target/release/libzone.dylib without an integrity check (NODE_ENV is not "production").
```

After changing the Rust code, run `knext ffi generate` again and restart the dev server: a process
keeps the library it loaded first. Plain `next dev` runs on Node and is refused on the first call
(see [Node is refused](#node-is-refused-and-why)).

### 5. Build and deploy

Nothing changes: `knext build`, `knext deploy` and `knext preview` notice `knext.ffi.json`,
cross-compile the library for the image first, and ship it beside the server. The build machine
needs a little more than Rust for that; see [Building images](#building-images).

To test code that imports the generated module outside Next.js, run Bun with the server condition,
or `server-only` throws on import:

```bash title="shell"
bun test --conditions=react-server
```

## Type mapping

| Rust (argument or return) | TypeScript | Notes |
|---|---|---|
| `i8` `i16` `i32` `u8` `u16` `u32` | `number` | checked before the call: a fraction, `NaN`, `Infinity`, a value outside the type's range or a non-number throws a `TypeError` naming the function and argument (`-0` is accepted and arrives as `0`) |
| `i64` `u64` `isize` `usize` | `bigint` | checked the same way against the 64-bit range; a `number` is refused, and an error message never prints more than a short number or a bit count |
| `f32` `f64` | `number` | anything but a `number` throws a `TypeError` |
| `bool` | `boolean` | anything but a `boolean` throws a `TypeError` |
| `&str`, `String` | `string` | UTF-8. Prefer `&str` for arguments: an owned `String` costs Rust a copy |
| `&[u8]`, `Vec<u8>` | `Uint8Array` | raw bytes, copied. Prefer `&[u8]` for arguments |
| `()` (return only) | `void` | |
| a `#[knext_ffi::record]` struct | an `interface` | crosses as JSON; see [Records and enums](#records-and-enums) |
| a `#[knext_ffi::record]` enum with unit variants | a union of string literals | crosses as JSON, as the variant's name |
| `Option<T>` | `T \| null` | crosses as JSON |
| `Vec<T>` (`T` is not `u8`) | `T[]` | crosses as JSON |
| `Result<T, E>` (return only, `E: Display`) | `T` | `Err(e)` throws a `RustError` whose `message` is `e.to_string()` |

- **64-bit integers are `bigint` everywhere**, including inside records, `Option` and `Vec`
  (`unit_cents: bigint`, `ids: bigint[]`), so values above 2^53 survive exactly. Inside JSON they
  travel as decimal strings; the generated code converts both ways and you never see the string.
- **Non-finite floats.** A plain `f32`/`f64` argument or return crosses as a raw number, so `NaN`
  and `Infinity` arrive intact. Inside JSON (records, `Option`, `Vec`) there is no `NaN` or
  `Infinity`, so a non-finite float is refused in every JSON position, `Option` included, in both
  directions. It never silently becomes `None` or `null`.
  - Sending one throws a `TypeError` before Rust is called, naming where the number sits, for
    example `reading(): argument "r.samples[1]" must be a finite number (JSON has no NaN or Infinity), got -Infinity`.
  - One coming back from Rust is refused with a `RustError` that names the path in the result:

    ```
    invalid input: knext-ffi: the return value cannot cross as JSON: result.samples[2]: f32 NaN is not finite (JSON has no NaN or Infinity)
    ```

    The message starts with `invalid input:` because it shares its status with decode failures,
    but the fault is in the value your Rust function returned, not in what you passed.
  - A JSON number too large for an `f32` field or argument is refused too, rather than becoming
    `Infinity`:

    ```
    invalid input: knext-ffi: argument `r` could not be decoded: the number does not fit a finite f32 at line 1 column 25
    ```
- **Inside JSON, `Vec<u8>` is a `number[]`.** For binary data, use a `&[u8]`/`Vec<u8>` argument or
  return directly, which crosses as raw bytes.
- **Empty values are fine.** An empty string or an empty `Uint8Array` can be passed and returned.
- **Not supported** (each is a compile error that names the type): generics and lifetime
  parameters, `char`, `i128`/`u128`, tuples, fixed-size arrays, raw pointers, `impl Trait`,
  function pointers, `async fn`, methods, `unsafe fn`, references other than `&str`/`&[u8]` (and
  any returned reference), `Result` as an argument, a nested `Option<Option<T>>` anywhere (`None` and
  `Some(None)` would both be `null`; `Option<Vec<Option<T>>>` is fine), data-carrying enums,
  generic or recursive records, and `#[serde(...)]` attributes on a record. For example:

```
error: knext-ffi: `char` is not supported: `char` has no TypeScript equivalent; pass a `String` or a `u32` code point; supported types are listed at https://knext-platform.dev/docs/rust-in-process#type-mapping
```

Every such error ends with that link to the table above.

## Records and enums

Mark a struct with named fields, or an enum whose variants carry no data, with
`#[knext_ffi::record]`. You do not add `serde` yourself; the attribute brings it in.

```rust title="rust/src/lib.rs"
use knext_ffi::{export, record};

/// A currency the shop sells in.
#[record]
pub enum Currency {
    Usd,
    Eur,
}

#[record]
pub struct LineItem {
    pub sku: String,
    pub quantity: u32,
    pub unit_cents: u64,
}

#[record]
pub struct Quote {
    pub currency: Currency,
    pub total_cents: u64,
    pub note: Option<String>,
}

/// Prices a cart.
#[export]
pub fn quote(items: Vec<LineItem>, currency: Currency) -> Result<Quote, String> {
    if items.is_empty() {
        return Err("the cart is empty".to_string());
    }
    let mut total: u64 = 0;
    for item in &items {
        let line = item
            .unit_cents
            .checked_mul(u64::from(item.quantity))
            .ok_or_else(|| format!("{}: line total overflows", item.sku))?;
        total = total.checked_add(line).ok_or("cart total overflows")?;
    }
    let note = (items.len() > 10).then(|| "bulk order".to_string());
    Ok(Quote { currency, total_cents: total, note })
}
```

`knext ffi generate` turns that into:

```ts title="src/generated/ffi/index.ts (excerpt)"
export interface LineItem {
  sku: string;
  quantity: number;
  unit_cents: bigint;
}

export interface Quote {
  currency: Currency;
  total_cents: bigint;
  note: string | null;
}

/** A currency the shop sells in. */
export type Currency = 'Usd' | 'Eur';

/** Prices a cart. … */
export function quote(items: LineItem[], currency: Currency): Quote;
```

Field and variant names cross **verbatim**: `unit_cents` stays `unit_cents`, and `Usd` stays
`'Usd'`. Rust doc comments on functions, records and enums become TSDoc. Unknown fields are
refused by Rust.

A route handler calling it, turning a `RustError` into a 400:

```ts title="src/app/api/quote/route.ts"
import { type LineItem, quote, RustError } from '../../../generated/ffi';

export async function POST(request: Request) {
  const body = (await request.json()) as {
    items: { sku: string; quantity: number; unit_cents: string }[];
  };
  const items: LineItem[] = body.items.map((item) => ({
    sku: item.sku,
    quantity: item.quantity,
    unit_cents: BigInt(item.unit_cents),
  }));
  try {
    const result = quote(items, 'Usd');
    return Response.json({ ...result, total_cents: result.total_cents.toString() });
  } catch (err) {
    if (err instanceof RustError) {
      return Response.json({ error: err.message }, { status: 400 });
    }
    throw err;
  }
}
```

`Response.json` cannot serialise a `bigint`, which is why the example converts `total_cents` to a
string.

Record, enum, `Option` and `Vec` arguments are **not** checked in JavaScript before the call,
except that every float inside them must be finite (see [Type mapping](#type-mapping)). A
value Rust cannot decode, such as an enum variant that does not exist, comes back as a `RustError`
whose message starts with `invalid input:` and names the argument:

```
invalid input: knext-ffi: argument `currency` could not be decoded: unknown variant `Gbp`, expected `Usd` or `Eur` at line 1 column 5
```

## Errors and panics

The generated module exports three error classes. All extend `Error`, work with `instanceof`, and
carry no Rust memory.

| What happened | What you get | The process |
|---|---|---|
| The function returned `Err(e)` | `RustError`; `message` is `e.to_string()`, `fn` is the function's name | keeps running |
| An argument Rust could not decode, or a return value that cannot cross as JSON (a `NaN` or `Infinity` inside it) | `RustError` whose message starts with `invalid input:`; for a return value it goes on `knext-ffi: the return value cannot cross as JSON:`, and the fault is in what Rust returned | keeps running |
| The function panicked | `RustPanicError`; `message` is the panic message, `fn` is the function's name | keeps running; the next call works |
| A number, `bigint`, `boolean`, string or `Uint8Array` argument of the wrong type or out of range, or a `NaN` or `Infinity` inside a record, `Option` or `Vec` argument | `TypeError`, before Rust is called, for example `greet(): argument "name" must be a string, got number` | keeps running |
| The library could not be loaded | `FfiLoadError`, explaining why | keeps running, but **every later call in that process throws the same error**: fix the cause and restart |

**A panic does not take the pod down.** Every exported function runs inside Rust's panic catcher,
so this:

```rust title="rust/src/lib.rs"
/// Splits `key=value`.
#[knext_ffi::export]
pub fn split_pair(input: &str) -> String {
    let (key, value) = input.split_once('=').expect("input has no '='");
    format!("{key}:{value}")
}
```

called as `split_pair('nope')` throws a `RustPanicError` whose message is `input has no '='`, and
the next call works. Rust also writes the panic's location to standard error, so it shows up in the
pod's logs:

```
thread '<unnamed>' (…) panicked at src/lib.rs:4:46:
input has no '='
```

Do not set `panic = "abort"` in the crate's profile: `knext-ffi` refuses to compile with it,
because a panic would then end the process instead of reaching JavaScript.

**What does take the pod down:** an abort, a segfault, a stack overflow, or `std::process::exit`,
in your Rust code or in anything it calls (including C libraries and `unsafe` code). These end the
whole zone process and every request it is serving, and Kubernetes restarts the container. This is
the cost of running in-process; a zone function is the tool when you need that isolation.

**A stale module is refused rather than called wrongly.** Each function's signature, and the shape
of every record and enum it uses, is checked when the library loads. If the Rust code changed and
the module was not regenerated, the first call throws an `FfiLoadError` that says the module is
stale and to run `knext ffi generate` and commit the result.

## Dynamic contexts only

In-process Rust runs **at request time only**: in Server Actions, route handlers, and dynamically
rendered pages and layouts. It does not run while `next build` prerenders, so a call from a
statically prerendered page, from `generateStaticParams`, or from `generateMetadata` of a static
route fails the build with:

```
Error [FfiLoadError]: In-process Rust runs only at request time. This call happened while `next build` was prerendering: Rust functions cannot be called during prerendering, from generateStaticParams, or from generateMetadata of a static route. Make the route dynamic: add `export const dynamic = 'force-dynamic'` to the route segment, or `await connection()` (from 'next/server') before the call.
```

The build has no library to load: the image gets its library when the Dockerfile that `knext build`, `knext deploy` and `knext preview` stage copies it
in, and the build itself runs before that. Make the route dynamic in one of two ways.

Mark the whole route segment dynamic:

```tsx title="src/app/hello/page.tsx"
import { greet } from '../../generated/ffi';

export const dynamic = 'force-dynamic';

export default function HelloPage() {
  return <p>{greet('World')}</p>;
}
```

Or wait for the request before the call:

```tsx title="src/app/hello/page.tsx"
import { connection } from 'next/server';
import { greet } from '../../generated/ffi';

export default async function HelloPage() {
  await connection();
  return <p>{greet('World')}</p>;
}
```

During `next build` this is always the error you get, even though there is no library. The
"cannot find the Rust library" error appears only at request time, and it means the library is
missing from where the module looked; see
[Where the library is loaded from](#where-the-library-is-loaded-from).

## Where the library is loaded from

Nothing is loaded when the module is imported. On the first call, it looks in this order:

1. **Beside the server executable**: `native/ffi/<target>/lib<name>.so` next to the compiled Bun
   server, which is where the Dockerfile that `knext build`, `knext deploy` and `knext preview` stage puts it
   in every image. The library must be listed in
   `native/.integrity.json` (written by the build) with a matching sha256. A missing manifest, an
   unlisted library or a different hash is refused, and nothing is loaded:

   ```
   knext ffi: refusing to load …/native/ffi/x86_64-unknown-linux-musl/libzone.so: sha256 mismatch
     expected 6f1c…
     actual   a93e…
   ```

   A hash covers the bytes read at that moment, not what the file holds later, so the module also
   refuses a library that anyone but root could change. Root must own the library, the integrity
   manifest and every directory from the library up to `/`: the ones below `native/`, `native/`
   itself, the directory beside the executable and each directory above that. None of them may be
   writable by its group or by everyone. A tree owned by any other user is refused, the user the app runs
   as included: that user could change the permissions of what it owns and write the library
   again, for example through a file-write bug in the app. Nothing is loaded:

   ```
   knext ffi: refusing to load …/native/ffi/x86_64-unknown-linux-musl/libzone.so: …/native/ffi/x86_64-unknown-linux-musl/libzone.so is writable by its group or by everyone (mode 0664), so its bytes could change after they were checked. The library and its integrity manifest must be owned by root and not writable by group or other (the Dockerfile that `knext build`, `knext deploy` and `knext preview` stage copies native/ with `COPY --chown=0:0 --chmod=a-w`), and the app should run as a non-root user; every directory from the library up to / must also be owned by root and not writable by group or other.
   ```

   A directory that fails is reported the same way: every one of them at once, with advice that depends on
   the situation, not on where the directory sits. A directory inside `native/` is yours to fix in place. A
   sticky directory (a shared one such as `/tmp`) that holds the executable or sits above it is shared with
   other software, so the advice is only to move the install under a directory root owns and closes, never to
   change the shared one. Any other failing directory (the one that holds the executable, or a directory above
   it that is not sticky, a world-writable one such as a `chmod 777 /app` included) may be part of your app's
   install or may be shared, and the refusal cannot tell which, so it gives both pieces of advice, each with
   its condition, and says that the executable needs a directory of its own. A home directory such as
   `/home/<user>` belongs to the account that owns it: the advice for it is to move the install, never to give
   the home directory to root. Where `/app` or `/app/native` is on the list and can be fixed in place, the
   refusal also names the one Dockerfile line that keeps a vinext app on the path `knext deploy` takes for its
   scaffolded `Dockerfile` (below), because that line closes those two and no other; and when a sticky
   directory is on the list together with others it says that fixing the others alone will not be enough,
   because the install has to move:

   ```
   knext ffi: refusing to load …/native/ffi/x86_64-unknown-linux-musl/libzone.so: 2 directories on the way to it cannot be trusted, so what is under them could be renamed or replaced after it was checked:
     /app/native is owned by uid 1000, but only root may own it
     /app is writable by its group or by everyone (mode 0775)
   Every directory from the library up to / must be a real directory, owned by root and not writable by group or other. To fix a directory inside native/: run `chmod go-w <dir>` (and `chown root <dir>` if root does not own it), as root; or, in a Dockerfile, `RUN chmod go-w <dir>` after the COPY that brought it in (a directory inside a copied tree keeps the build host's mode). A directory that holds the executable or sits above it: if it is part of your app's install, run `chmod go-w <dir>` (and `chown root <dir>` if root does not own it), as root, or, in a Dockerfile, `RUN chmod go-w <dir>` after the COPY that brought it in. If it is shared with other software, or is a home directory such as /home/<user>, do not change its owner or mode (never give a home directory to root): move the install instead. The executable needs a directory of its own, owned by root and closed to group and other, such as /opt/<app>. In a vinext app's Dockerfile, put exactly `RUN chmod go-w /app /app/native` directly after the `COPY --chown=0:0 --chmod=a-w native /app/native` line: that keeps the app on the known-good path, and a chmod anywhere else, or one per directory, takes the deploy off it (`knext ffi check` says whether the line is there).
   ```

   ```
   knext ffi: refusing to load …/native/ffi/x86_64-unknown-linux-musl/libzone.so: 2 directories on the way to it cannot be trusted, so what is under them could be renamed or replaced after it was checked:
     /srv/app/native is owned by uid 1000, but only root may own it
     /srv is writable by its group or by everyone (mode 1777)
   Every directory from the library up to / must be a real directory, owned by root and not writable by group or other. To fix a directory inside native/: run `chmod go-w <dir>` (and `chown root <dir>` if root does not own it), as root; or, in a Dockerfile, `RUN chmod go-w <dir>` after the COPY that brought it in (a directory inside a copied tree keeps the build host's mode). A sticky directory (a shared one such as /tmp) that holds the executable or sits above it is shared with other software, so do not change its owner or mode: move the install under a root-owned, closed directory such as /opt/<app> instead. The other directories on this list can be fixed, but that alone will not make this install load while a sticky one is on the way: the install has to move.
   ```

   ```
   knext ffi: refusing to load …/native/ffi/x86_64-unknown-linux-musl/libzone.so: 2 directories on the way to it cannot be trusted, so what is under them could be renamed or replaced after it was checked:
     /srv/app is owned by uid 1000, but only root may own it
     /srv is writable by its group or by everyone (mode 0775)
   Every directory from the library up to / must be a real directory, owned by root and not writable by group or other. A directory that holds the executable or sits above it: if it is part of your app's install, run `chmod go-w <dir>` (and `chown root <dir>` if root does not own it), as root, or, in a Dockerfile, `RUN chmod go-w <dir>` after the COPY that brought it in. If it is shared with other software, or is a home directory such as /home/<user>, do not change its owner or mode (never give a home directory to root): move the install instead. The executable needs a directory of its own, owned by root and closed to group and other, such as /opt/<app>.
   ```

   Each refusal carries only the advice that applies to the directories it lists. Check the parent you choose
   before you install under it: on some hosts `/opt` itself is writable by everyone, and a tree under it is then
   refused with `/opt` named. Pick another parent that root owns and closes to group and other, such as
   `/var/lib`. A symbolic link or a regular file where a directory belongs is named as such, and told to be
   replaced with the directory.

   This protects against a writer that is not root, the app's own user among them. It does not
   protect against root, a process allowed to bypass file permissions, a second writable mount of
   the same files, or an access control list: only the permission bits are read, and on macOS an
   ACL can grant write access that they do not show. "Allowed to bypass file permissions" means
   any capability that is equivalent to root, for example `CAP_DAC_OVERRIDE`, `CAP_FOWNER`, `CAP_CHOWN`,
   `CAP_SETUID`, `CAP_SYS_ADMIN` (mount), `CAP_SYS_PTRACE`, `CAP_MKNOD`, `CAP_SYS_MODULE`, `CAP_SYS_RAWIO`
   and `CAP_BPF`; the list gives examples and is not a boundary. A container that drops every capability and sets
   `allowPrivilegeEscalation: false`, as the pods the knext operator creates do, takes that class away
   from the app, but not `uid 0` itself: an app that runs as root owns the tree whatever it has dropped.
   Run it as a non-root user too (`runAsNonRoot` in a pod, which the operator sets unless
   `spec.security.runAsNonRoot` says otherwise); for a container you run yourself, use
   `--cap-drop=ALL --security-opt no-new-privileges --user 65532`. Two more limits: a file-write bug that
   lets someone write at an offset of a file as the app's user can reach the running process through
   `/proc/self/mem`, which no rule about files covers; and a container that runs in a user namespace is two
   cases. Rootless Podman or Docker: the image's files belong to the host user who started the container, who
   can write them whatever the app runs as inside, so running as a non-root user inside does not remove that
   writer. A pod with `hostUsers: false`: the image's files belong to the pod's own root, which is host root
   where the filesystem supports idmapped mounts and otherwise the root of a uid range given to that pod alone
   (not host root); no other user on the host owns or can write them either way, so running as a non-root
   user inside restores the guarantee, and an app that runs as `uid 0` inside still owns the tree. There is no setting that turns the check off.

   The Dockerfile that `knext build`, `knext deploy` and `knext preview` stage already has this layout. In your own
   Dockerfile, use this shape. Every directory above `native/`, up to `/`, must be owned by root too, and not writable by group
   or other: a directory that someone else can write lets them rename or replace the library, or
   the directory itself, before the process opens it, and the same is true of any directory above it.
   The module opens the manifest and the library without following symbolic links, judges each file it
   opened by its owner and mode, looks at every directory on the way (a symbolic link in place of one
   is refused), and refuses a tree whose directories changed while the library was being checked.
   `WORKDIR` creates `/app` that way when it does not exist yet, and a `COPY` into it leaves it so:

   ```dockerfile title="Dockerfile"
   ARG BASE_IMAGE
   FROM ${BASE_IMAGE}
   WORKDIR /app
   COPY server /app/server
   COPY --chown=0:0 --chmod=a-w native /app/native
   RUN chmod go-w /app /app/native
   USER 65532:65532
   ENTRYPOINT ["/app/server"]
   ```

   The `RUN chmod go-w` line closes `/app` and `/app/native` themselves, so the result does not depend on
   the mode your builder gives the destination of a `COPY` (BuildKit makes it 0755; another builder may
   use the mode of the build machine). Build it with `--build-arg BASE_IMAGE=<your runtime base image>`,
   where `server` is your compiled server executable and `native/` is the tree `knext ffi build` stages. A `chown` of the
   app directory to the app user (`RUN chown -R app /app`) does not pass.

   An app scaffolded for the vinext build (a Bun single executable) is built from the `Dockerfile` it was
   scaffolded with. That file is yours and knext does not edit it, so the line is yours to add: put
   `RUN chmod go-w /app /app/native` directly after the `COPY` that brings `native/` in (and so before `USER`),
   as in the recipe above, and change nothing else in the file. `knext ffi init` prints that line when your
   `Dockerfile` copies `native/` to `/app/native` and does not have it directly after that `COPY`, and so do
   `knext ffi generate` and `knext ffi check`. They do not read what your commands do. They confirm one form,
   and say nothing only for it: the scaffolded `COPY` of `native/`, then that line as the very next line of the
   file, byte for byte, and after it nothing but `ENV`, `ARG`, `LABEL`, `EXPOSE`, `USER`, `WORKDIR`, `ENTRYPOINT`,
   `CMD`, `HEALTHCHECK`, `STOPSIGNAL` and a read-only check of the shape
   `RUN test -f <path> || { echo "<text>" >&2; exit 1; }` (the scaffolded `RUN test -f /app/native/.integrity.json || { ... }`
   is one, written over several lines; the text is a plain string with no `$`, backtick or backslash). The whole file has to be clean as well,
   and that is judged before anything else is looked at: no `<<` anywhere (a heredoc's body is not `Dockerfile` text),
   no `escape` or `syntax` parser directive on any line (a byte-order mark or an indent does not hide one; the
   scaffolded file's own pinned `# syntax=` line, as its first line and byte for byte, is the one that passes),
   no `SHELL` or `ONBUILD` instruction in any stage (a parent stage runs its `ONBUILD` triggers in the stage
   that builds on it), no line that does not start with an instruction Docker knows (BuildKit reads a
   `// syntax=` line as a directive), no line ending in a backslash that no space or tab precedes (a lone
   backslash, or a word split in two), and no character that another reader may take for something else: any
   space-like character but a space and a tab (a no-break space, a form feed), a control or invisible format
   character (a byte-order mark), an invalid byte, or a carriage return that does not end a line (visible
   non-ASCII text, such as a dash in a comment, is fine). A `Dockerfile` that fails any of these is not
   confirmed, and is told so whenever it mentions native at all.
   Anything else is not confirmed: any other `RUN`, a `COPY` or `ADD` after the line, an instruction they do not
   know, a blank line or a comment between the `COPY` and the line, a space or anything else on either of the two
   lines, or a `COPY` of `native/` that is not the scaffolded one. They then say which of these it was, and never say that the loader will accept the directories.
   A `Dockerfile` that closes them some other way may load, but knext cannot confirm it, and `knext deploy`
   takes the slower path described next. An app built with another builder is told none of this, because those
   builds stage a `Dockerfile` that already has the line; an app whose build cannot be read (a
   `knext.config.ts` that does not load) is told as if it were vinext.

   Adding that line keeps your app on the path `knext deploy` takes for the scaffolded file. `knext deploy`
   recognises the scaffolded `Dockerfile` byte for byte, as one that copies your host build, and uploads the
   assets from that build while the image is pushed; any other `Dockerfile` has its assets taken from the built
   image and checked against it, which is slower. It recognises the scaffolded file with just this one line
   directly after the `COPY` that brings `native/` in as well, so an app that follows the advice keeps the build
   and the asset upload it has; a blank line, a comment, another place for the line, or any other edit takes it
   off that path. Under BuildKit nothing changes for an existing app: both directories are already root's and
   closed, so it loads without the line. With another builder the first call of the module is refused, and the
   message says how to fix the directories and, for a vinext app, which one line to add. A closing `chmod`
   anywhere else, or one per directory, closes them too and the module loads, but it takes `knext deploy` to
   the slower path.

   If your Dockerfile copies a whole source tree instead (`COPY . /app`), the directories inside the copy
   keep the mode they have on the machine that builds the image, and a build machine with a `umask` of
   `002` makes them group-writable (`0775`), which the module refuses. Close them after the copy:

   ```dockerfile title="Dockerfile.copied-tree"
   COPY --chown=0:0 . /app
   RUN chmod -R go-w /app
   ```

   A compiled binary you run outside a container needs the same ownership, and so does every directory
   above it. Hand the directory that holds the executable and `native/` to root, remove group and
   other write, and run the binary as an ordinary user. The commands below hand over the whole
   directory, `-R`, so they check it first and change nothing unless it is exactly an app: after following a link to the real directory,
   it must hold `native/` (with its `.integrity.json`) and one other entry, your executable as a regular file, and nothing else,
   and it must not be a system, home or temporary directory (`/`, `/opt` itself, `/tmp`, `/var/lib`, `/dev`, `/run`, `/etc`, a home directory or anything under one, and, on macOS, what `/tmp`, `/etc` and `$TMPDIR` really are under `/private`, and the like).
   A path that is not absolute, does not exist or fails either check is refused with the reason, and nothing is run.
   The commands need bash and refuse unless bash runs them, before they look at anything: `sh` where it is bash (as on macOS) runs them; any other shell, `dash` and `zsh` included, does not. `zsh` stops with "no matches found" on a glob that matches nothing, which would refuse a good directory for the wrong reason, and `local`, which the commands use, is not part of POSIX `sh`.
   `/opt/<app>` and `/usr/local/<app>` pass. The directories above it must
   already be root's and closed to group and other: a root-owned `/opt/<app>` is fine, a home directory or
   `/tmp` is not, and the refusal names the directory:

   ```bash title="own-binary.sh"
   # APP_DIR: the directory that holds your server executable and its native/ directory, and
   # nothing else (for example /opt/myapp). All of it is handed to root, so this checks first that
   # it is exactly that, after following any link to the real directory: native/ with its
   # .integrity.json, and one other entry, the executable, a regular file; and that it is not a
   # system, home or temporary directory. It needs bash and refuses unless bash runs it.
   real_dir() {
     local p lead
     p=$(cd -P -- "$1" 2>/dev/null && pwd -P) || return 1
     lead=${p%%[!/]*}
     printf '/%s\n' "${p#"$lead"}"
   }
   unsafe_dir() {
     local d
     for d in /tmp /var/tmp /home /Users /root /private/tmp /private/var /private/etc; do
       case "$1" in "$d" | "$d"/*) return 0 ;; esac
     done
     for d in /bin /boot /dev /etc /lib /lib64 /proc /run /sbin /sys /usr/bin /usr/lib /usr/libexec /usr/sbin /usr/share; do
       case "$1" in "$d" | "$d"/*) return 0 ;; esac
     done
     case "$1" in
       / | /opt | /srv | /mnt | /media | /nix | /snap | /usr | /usr/local | /usr/local/bin | /usr/local/lib | /usr/local/sbin | /usr/local/share | /var | /var/cache | /var/lib | /var/log | /var/spool | /var/www) return 0 ;;
     esac
     [ "$2" = / ] && return 1
     case "$1/" in "$2"/*) return 0 ;; esac
     case "$2/" in "$1"/*) return 0 ;; esac
     return 1
   }
   holds_only_app() (
     native=0 exe=0
     for e in "$1"/* "$1"/.[!.]* "$1"/..?*; do
       [ -e "$e" ] || [ -L "$e" ] || continue
       if [ "${e##*/}" = native ]; then
         [ -d "$e" ] && [ ! -L "$e" ] && [ -f "$e/.integrity.json" ] && [ ! -L "$e/.integrity.json" ] || return 1
         native=1
       else
         [ -f "$e" ] && [ ! -L "$e" ] || return 1
         exe=$((exe + 1))
       fi
     done
     [ "$native" = 1 ] && [ "$exe" = 1 ]
   )
   if [ -z "${BASH_VERSION:-}" ]; then
     echo "refusing: this needs bash, and it is running under another shell" >&2
     false
   elif [ -z "${APP_DIR:-}" ] || [ "${APP_DIR#/}" = "$APP_DIR" ]; then
     echo "refusing: APP_DIR must be an absolute path, such as /opt/myapp" >&2
     false
   elif ! R=$(real_dir "$APP_DIR"); then
     echo "refusing: $APP_DIR is not a directory that exists" >&2
     false
   elif unsafe_dir "$R" "$(real_dir "${HOME:-/}" || echo /)"; then
     echo "refusing: $R is a system, home or temporary directory, and handing it to root would change everything else in it: use a directory of its own, such as /opt/myapp" >&2
     false
   elif ! holds_only_app "$R"; then
     echo "refusing: $R must hold only this app: native/ (with its .integrity.json) and your one executable, and nothing else" >&2
     false
   else
     sudo chown -R root:root "$R"
     sudo chmod -R go-w "$R"
   fi
   ```

   A volume mounted at `native/` or above it (a shared volume, a sidecar's, or one made group-writable
   by `fsGroup`) is refused unless root owns everything on it and group and other cannot write it. One
   that passes is still writable through its other mounts, which the module cannot see, so do not share
   it with a sidecar or mount it writable anywhere else. A symbolic link where the library,
   `native/.integrity.json`, `native/` or any directory inside the tree should be is refused too, whatever it
   points at: keep `native/` as the plain files and directories that `knext ffi build` stages and a `COPY`
   carries over.

   The executable's own path is judged where it really is. Bun reports `process.execPath` already resolved,
   so an install reached through such a link loads (a `current -> releases/12` link, `/var` where it is a
   link, a merged `/usr`), and the directories judged are those of the real tree. The module also compares
   the directory beside the executable with its real path and refuses a difference, but only as a
   fail-closed assertion: it fires only when code has replaced `process.execPath` with a path that is
   relative or goes through a link, and the message says which of the two it is. A deploy tool that keeps
   releases in a directory it owns (Capistrano and its relatives put them under `releases/`) is refused, not
   for its link but because that directory belongs to the deploy user. Put `deploy_to` under a parent where
   every directory from that parent up to `/` is root-owned and closed to group and other, make `deploy_to`,
   `releases/` and each release root-owned and closed to group and other, and never change anything above
   `deploy_to`. Switching `current` and `deploy:cleanup` need root too, as does the step that puts the files in
   place: the deploy user can no longer write to any of it.

2. **The development build**, only when `NODE_ENV` is not `production`: `rust/target/release/` or
   `rust/target/debug/`, whichever is newer, with no integrity check and the one-line notice above.
3. Otherwise the call throws an `FfiLoadError` listing every path it tried.

There is no environment variable that points it somewhere else. One consequence: `bun --bun next
start` after a plain `next build` is refused, because there is no `native/` beside the Bun binary
and `NODE_ENV` is `production`. Use `bun --bun next dev` locally, and an image built from
the Dockerfile that `knext build`, `knext deploy` and `knext preview` stage everywhere else. An image built for one CPU architecture and run on another is refused with a
message naming both.

## Blocking and Workers

A call is **synchronous**: it blocks the zone's JavaScript thread, and with it every other request
on that pod, until it returns. Keep each call on the request path **under about a millisecond**.

Measured per-call costs through a prototype of the generated wrapper, built before this feature
shipped, on an Apple M1 Pro (macOS) with Bun 1.4.2. The shipped module may differ. The machine was
shared during the run, so treat these as orders of magnitude (runs varied up to about 2x); Linux
images will differ too.

| Call | Time per call |
|---|---|
| `add(i32, i32) -> i32` | 10–11 ns |
| `sum(Vec<u8>)`, 64 bytes (the argument is copied into a `Vec`) | 118–126 ns |
| `greet(&str) -> String`, a short string | 330–460 ns |
| `greet(&str) -> String`, 1 KiB | 0.84–1.96 µs |
| `mid(Point, Point) -> Point`, two records in and one out (JSON) | 0.95–3.2 µs |
| the first call in a compiled Bun executable, including the integrity check and loading the library | about 1.9 ms, once |

Strings cost their UTF-8 encoding, and records cost their JSON; scalar calls are nearly free.

**For work that takes longer, use a zone function**: it runs in its own pod and never blocks the
zone.

A Bun `Worker` can also call the generated module, off the main thread. Each Worker imports the
module and opens the library itself, but opening the same file twice in one process returns the
same loaded library, so the process holds one copy of the library. Its Rust statics (a `static`,
a `OnceLock`, a `LazyLock`) are therefore shared by the main thread and every Worker, and calls from
different Workers can run at the same time, so anything they share must be safe to use from
several threads at once:

```ts title="stretch-worker.ts"
import { stretch } from './generated/ffi';

declare const self: Worker;

self.onmessage = (event: MessageEvent<{ data: Uint8Array; rounds: number }>) => {
  const { data, rounds } = event.data;
  self.postMessage(stretch(data, rounds));
};
```

```ts title="main.ts"
const worker = new Worker(new URL('./stretch-worker.ts', import.meta.url));

// One call at a time, for brevity.
function stretchOffThread(data: Uint8Array, rounds: number): Promise<Uint8Array> {
  return new Promise((resolve, reject) => {
    worker.onmessage = (event: MessageEvent<Uint8Array>) => resolve(event.data);
    worker.onerror = (event) => reject(new Error(event.message));
    worker.postMessage({ data, rounds });
  });
}
```

Run it with `bun --conditions=react-server main.ts`, for the same `server-only` reason as tests.
**This works in Bun directly, not inside a Next.js app**: neither bundler produces a working
server-side Worker. Turbopack copies the Worker's file into the build as a plain asset, so its
imports do not resolve (in `next dev` and after `next build`), and a webpack build bundles it but
then loads it from a URL that does not exist on the server. Both were checked with Next.js 16.3.5
on Bun 1.4.2. Inside the
zone, keep calls short or move the work to a zone function.

## Slow calls

A call that blows the budget is easy to miss: it shows up only as tail latency, or as requests
dropped when a pod scales down. So the generated module times every Rust call, and when one takes
longer than a threshold it counts the call and logs it.

This makes a slow call **visible**. It does not make it any shorter: while a Rust call runs,
nothing else runs in that process, and knext cannot interrupt it (neither can Bun).

### The threshold

`KNEXT_FFI_SLOW_CALL_MS` sets the threshold, in milliseconds. The default is **50 ms**. Fractions
work (`2.5`), and `0` turns counting and the log line off. The module reads it on the first call.
Any other value is ignored, with a warning, and the default is used:

```
knext ffi: ignoring KNEXT_FFI_SLOW_CALL_MS="fast": it must be a number of milliseconds (0 turns slow-call counting off). Using 50.
```

Timing a call reads the clock twice. Measured on an Apple M1 Pro (macOS) with Bun 1.4.2, that took
`add(i32, i32) -> i32` from about 4.5 ns to about 69 ns per call through the shipped module. It is
the same fixed cost for every call, so it matters only on a hot path of scalar calls, and `0` does
not remove it.

### The log line

The first slow call to each function logs one line with the time it took:

```
knext ffi: stretch() took 212.4 ms, over the 50 ms slow-call threshold (KNEXT_FFI_SLOW_CALL_MS). A Rust call blocks this process for its whole duration: no other request is served and a shutdown cannot drain until it returns. Move long work to a zone function. Later slow calls to stretch() are counted in knext_ffi_slow_calls_total, not logged.
```

Later slow calls to the same function are counted but not logged, so a slow function on a hot
path cannot flood the log.

### The metrics

| Metric | Type | Meaning |
|---|---|---|
| `knext_ffi_slow_calls_total` | Counter, labelled `fn` | Calls slower than the threshold, per Rust function. Every function is listed, at 0, once the library has loaded. |
| `knext_ffi_load_seconds` | Gauge, labelled `lib` | How long the first call spent loading the library: finding it, checking its sha256 against the integrity manifest, and opening it. Set once per process. |

On the default standalone build, both are served on the app's metrics port (`METRICS_PORT`, `:9464`
by default), the one the shipped scrape collects, from the first call on. They need the app's metrics listener, which the scaffolded
`instrumentation.ts` starts. The `fn` and `lib` labels come from the library's own export list, so
the set of series is fixed.

Both the standalone build and the single-executable (vinext) build serve them on the metrics port,
once the library has loaded. Before the first call there are no `knext_ffi_*` series.

One limit:

- **A Bun `Worker` keeps its own count**, which the metrics port does not read. A slow call in a
  Worker is logged but not counted. It also blocks only that Worker, not the requests.

To be told about slow calls, alert on the counter, for example
`increase(knext_ffi_slow_calls_total[5m]) > 0`.

### What a slow call does to the pod

- **No other request on the pod is served** until it returns. Requests queue behind it, and the
  autoscaler sees the concurrency pile up on that pod.
- **Health checks wait too**, so a long call can mark the pod unready.
- **Shutdown cannot drain.** On `SIGTERM`, knext stops taking requests and drains the ones in
  flight, with a hard cap. Both are timers on the same thread, so neither can fire until the call
  returns. A call that runs past the pod's termination grace period ends with the pod killed
  (`SIGKILL`), and every request still in flight on it is dropped.
- **The first call after a cold start is slower**: it also loads the library and hashes it for the
  integrity check. `knext_ffi_load_seconds` shows that cost; it is not counted as a slow call.

The fix is the one above: keep each call short, and move long work to a zone function.

## Building images

When the app has `knext.ffi.json` and runs on Bun, `knext build` (and `knext deploy` and
`knext preview`, which build the same way) runs `knext ffi build` **before** the project build:

1. **Checks the toolchain** and stops with the install command for anything missing: Rust and the
   musl target, the four cargo tools and zig, each at its pinned version (see below).
2. **Checks the dependencies** before anything is compiled: `rust/Cargo.lock` may take git
   dependencies only from the knext repository, and `cargo deny check` must pass (see
   [Supply chain](#supply-chain)).
3. **Cross-compiles** the crate for the image:
   `cargo auditable zigbuild --release --locked --target <target>` with
   `-C target-feature=-crt-static`, so the library links against the musl C library the
   Alpine-based image has. `--locked` means `rust/Cargo.lock` must be committed.
4. **Checks what the library links.** Only `libc.so`, musl's own `libc.musl-<arch>.so.1` and
   `ld-musl-<arch>.so.1`, and `libgcc_s.so.1` are allowed. A glibc library (`libc.so.6`,
   `ld-linux-*`) would crash on the image, so the build stops and names it. The library must also
   carry the crate list `cargo auditable` embeds.
5. **Writes an SBOM** of the crate's dependencies for the target with `cargo cyclonedx`.
6. **Stages** the library as `native/ffi/<target>/lib<name>.so` with a `provenance.json` and an
   `sbom.cdx.json` beside it, replacing only `native/ffi/`.
7. **Checks the committed module** against the library it just built. If they differ, the build
   stops: run `knext ffi generate` and commit the result.

Then the normal build runs, and the image ships `native/` beside the server executable with a
checksum manifest (`native/.integrity.json`) that the module verifies before loading. This works on
every Bun build target (Turbopack, webpack and vinext). An app without `knext.ffi.json` builds
exactly as before.

Images are built for `linux/amd64`, so the target is `x86_64-unknown-linux-musl`. `knext ffi build`
also accepts `aarch64-unknown-linux-musl`. What knext checks today is that the library links for
both targets with no glibc dependency; a load test on the Alpine runtime image (x64 and arm64, with
a read-only root file system) is one of the conditions for [leaving Beta](#leaving-beta).

`knext build --skip-next` and `knext deploy --skip-build` do not run `knext ffi build`: they reuse
whatever is staged under `native/ffi/`, and stop with an error if nothing is staged for the image's
architecture. `knext deploy --image` builds nothing from the checkout, so it needs nothing staged.

**What the build machine needs**, including the CI runner that builds images:

- **Rust**, from [rustup.rs](https://rustup.rs). The crate's `rust-toolchain.toml` selects the
  version and lists the musl targets, so rustup installs them on first use. If a target is still
  missing, the build names it:

  ```bash title="shell"
  rustup target add x86_64-unknown-linux-musl
  ```

- **Four cargo tools, at these exact versions.** `cargo-zigbuild` cross-compiles against musl from
  macOS or any Linux, `cargo-deny` checks the dependencies, `cargo-auditable` embeds the crate list
  in the library, and `cargo-cyclonedx` writes the SBOM. A missing tool, or any other version, stops
  the build with the command that installs the pinned one:

  ```bash title="shell"
  cargo install --locked --version 0.23.4 cargo-zigbuild
  cargo install --locked --version 0.20.2 cargo-deny
  cargo install --locked --version 0.7.7 cargo-auditable
  cargo install --locked --version 0.5.9 cargo-cyclonedx
  ```

  `cargo-auditable` has no version flag, so knext reads its version from the record
  `cargo install` keeps. Install it with `cargo install`, not a system package manager.

- **zig 0.17.0**, which supplies the musl C library to link against. A `zig` on `PATH` is used only
  if `zig version` prints exactly `0.17.0`; a zig of any other version on `PATH` is refused, never
  silently replaced. With no zig on `PATH`, knext downloads the pinned zig 0.17.0 archive from
  ziglang.org and checks its sha256 against the one it pins; a mismatch stops the build and nothing
  is installed. Downloads are pinned for `linux-x86_64`, `linux-aarch64` and `macos-aarch64`; on
  any other host (an Intel Mac, say), install zig 0.17.0 from
  [ziglang.org/download](https://ziglang.org/download/) and put it on `PATH`.

  The archive is cached in `$KNEXT_CACHE_DIR/zig/0.17.0` if `KNEXT_CACHE_DIR` is set, otherwise
  `$XDG_CACHE_HOME/knext/zig/0.17.0`, otherwise `~/.cache/knext/zig/0.17.0`. The extracted zig is
  not cached: every build checks the cached archive's sha256 again and extracts it into a private
  temporary directory of its own, which it removes when done. That costs about 10 s per build;
  putting zig 0.17.0 on `PATH` skips it.

  The download gives up after 10 minutes, and it does not use `HTTPS_PROXY`. Behind a proxy, or
  where the build machine cannot reach ziglang.org, install zig 0.17.0 on `PATH` instead.

`knext ffi generate` and `knext ffi check` need only Rust.

## Node is refused, and why

`bun:ffi` exists only in Bun, so an app with `knext.ffi.json` cannot use the Node runtime. This
does not change anything for apps that do not opt in; the Node runtime is still fully supported.

At build time, `knext build`, `knext deploy` and `knext preview` refuse before doing any work,
including with `--skip-next`, `--skip-build` and `--image`:

```
knext: in-process Rust (bun:ffi) needs the Bun runtime, but this app builds for Node.

  knext.ffi.json opts this app into in-process Rust, and knext.config.ts resolves
  runtime: 'node'. bun:ffi exists only in Bun, so the build stops here instead of
  shipping an image whose Rust calls would fail on the first request.

  Fix one of:
    - use the Bun runtime: remove runtime: 'node' from knext.config.ts (Bun is the default);
    - or move this code to a zone function (knext add function <name> --lang rust),
      which runs on both runtimes.
```

At run time, a call made under Node (for example `next dev` without `--bun`) throws:

```
FfiLoadError: In-process Rust (bun:ffi) runs only on Bun; this process is Node v24.14.0. Run the app with Bun (bun --bun next dev), or call this code through a zone function.
```

Importing the module under Node is fine; only calling it fails. So a page that imports it still
renders, and only the call throws.

## Self-contained mode is not supported

The [self-contained mode](/docs/build-pipeline) ships nothing beside the executable, but the Rust
library has to sit on disk beside it. An app with `knext.ffi.json` and `selfContained: true` (or
`--self-contained`) is refused before any build work:

```
knext: in-process Rust (bun:ffi) does not work in self-contained mode.

  knext.ffi.json opts this app into in-process Rust, and this build is
  self-contained (selfContained: true in knext.config.ts, or --self-contained).
  That mode ships nothing beside the executable, but the Rust library has to be
  loaded from disk beside it (native/ffi/), so the build stops here.

  Fix one of:
    - turn self-contained mode off: remove selfContained: true from knext.config.ts
      and drop --self-contained;
    - or move this code to a zone function (knext add function <name> --lang rust),
      which runs on both runtimes.
```

## Supply chain

Every image build runs these checks, and stops on the first one that fails, before anything ships:

- **Pinned tools.** zig and the four cargo tools must be the exact versions listed in
  [Building images](#building-images), and a zig knext downloads is checked against the sha256 it
  pins. The versions used are recorded in `provenance.json`.
- **Locked dependencies.** The cross-compile is `--locked`, so `rust/Cargo.lock` must be committed
  and is used as it is. The Rust version is pinned by `rust/rust-toolchain.toml`, and `knext-ffi` by
  a full git commit, not a branch or tag.
- **Git sources.** Every git dependency in `rust/Cargo.lock` must come from
  [https://github.com/getknext-dev/knext](https://github.com/getknext-dev/knext), where the `knext-ffi` crates live. Depend on anything else
  through a crates.io release. This is checked from `Cargo.lock` itself, so editing `deny.toml`
  does not widen it.
- **`cargo deny check`** runs before every build. Its bans, licences and sources checks run under
  `rust/deny.toml`, which `knext ffi init` writes (crates.io plus the knext repository as sources,
  a starting licence list to review, yanked crates refused). Any RustSec advisory against a
  dependency fails the build unless `rust/advisory-allowlist.json` accepts it (below).
- **`cargo auditable`** wraps the cross-compile and embeds the list of crates in the library, so
  image scanners that read it can see the Rust dependencies. A library without that list is
  refused.
- **A CycloneDX SBOM** of the crate's dependencies for each target, from `cargo cyclonedx`, staged
  as `native/ffi/<target>/sbom.cdx.json`. It ships in the image and is covered by the integrity
  manifest like everything else under `native/`.
- **A provenance record** beside each library, `native/ffi/<target>/provenance.json`, also in the
  image, with these fields:
  - `version`: the format of this file, `1`.
  - `crate`: the crate's name and version.
  - `cargoLockSha256`: the sha256 of `rust/Cargo.lock`.
  - `rustc`: the `rustc -V` line.
  - `zigbuild`: the `cargo-zigbuild` version.
  - `target`: the target triple.
  - `profile`: `release`.
  - `knextFfiRev`: the `knext-ffi` commit `Cargo.lock` resolved.
  - `library`: the library's file name and sha256.
  - `tools`: the version of each cargo tool, and zig's version and where it came from (`path`, or
    `ziglang.org` with the sha256 of the archive it was extracted from).
  - `advisoriesAccepted`: the advisory ids the allowlist accepted for this build.
  - `sbom`: the SBOM's file name and sha256.
- **An integrity check at load.** `native/.integrity.json` holds the sha256 of every file under
  `native/`, written at build time; the module refuses to load a library that is not listed or does
  not match. It then loads the library through the same open file it checked (`/proc/self/fd` on
  Linux, which needs `/proc` mounted, as it is in a normal container; `/dev/fd` on macOS), so a
  file renamed or symlinked over the path between the check and the load is not the one loaded.
  An open file pins the file, not its bytes, so an in-place write, a hard link to the same file or
  a writable memory map by someone else would still change what runs. The module therefore also
  applies an ownership rule, judged by owner and mode: root must own the library, the integrity
  manifest and every directory from the library up to `/`, and none of them may be writable by a
  group or by everyone. Every directory counts because someone who can write one can rename the
  tree out from under the checks; with all of them root's, no other user can. The manifest counts
  because it is what says which file may load: one that someone else could write would let any
  library root owns pass. Both files are opened without following a symbolic link, and only a plain
  file is read. The directories are looked at again after the library is hashed, so a tree renamed
  over the real one in between is refused. A different owner (the app's own user included, since it can change the
  permissions of what it owns) and write access for a group or for everyone are each refused. The
  Dockerfile that `knext build`, `knext deploy` and `knext preview` stage copies `native/` owned by root and
  read-only (`COPY --chown=0:0 --chmod=a-w`), and the app runs as a non-root user, so an image built from it
  passes. A shared,
  sidecar or `fsGroup` volume at `native/` does not, unless root owns it and group and other cannot
  write it, and even then it stays writable through its other mounts. This does not stop root: a
  process running as root, or one allowed to bypass file permissions, can still change the library,
  and so can a second, writable mount of the same files or an access control list that grants write
  access (only the permission bits are read).
- **The module matches the library.** The build regenerates the module from the library it is about
  to ship and stops on any difference, and the module itself checks the library's functions when it
  loads.
- **No glibc surprises.** The link check refuses a library the image cannot load.

### Accepting an advisory

First try to upgrade the affected crate (`cargo update -p <crate>`). If you cannot fix it yet,
accept that one advisory in `rust/advisory-allowlist.json`, beside `deny.toml`:

```json title="rust/advisory-allowlist.json"
{
  "allow": [
    {
      "id": "RUSTSEC-2021-0003",
      "justification": "The affected function is never called by this crate.",
      "added": "2026-10-14",
      "expires": "2027-01-14"
    }
  ]
}
```

- `id`: the RustSec id, `RUSTSEC-YYYY-NNNN`.
- `justification`: why the risk is acceptable here; it may not be empty.
- `added`: the date the entry was added, `YYYY-MM-DD`.
- `expires`: optional, a `YYYY-MM-DD` date. After it, the entry stops covering the advisory and the
  build fails again until someone re-justifies it.

A malformed file or entry fails the build. The build prints each advisory it accepted, and
`provenance.json` records them. An advisory listed only in the `ignore` list of `deny.toml` is
still refused: that list carries no date or reason, so only the allowlist can accept an advisory.

## Reserved names

A Rust name becomes a TypeScript name verbatim, so `knext ffi generate` refuses names that would
not work there, and says which:

```
"process" cannot be a generated function name: rename it in Rust (it must be an identifier that is not a JavaScript reserved word or a name the generated module declares)
```

- **Function and argument names** cannot be a JavaScript reserved word (`new`, `delete`, `class`,
  `await`, `yield`, …), `undefined`, `NaN`, `Infinity`, `arguments` or `eval`, or a name the
  generated module uses itself: `RustError`, `RustPanicError`, `FfiLoadError`, `ArrayBuffer`,
  `BigInt`, `DataView`, `Error`, `JSON`, `Math`, `Number`, `Record`, `String`, `TextEncoder`,
  `TypeError`, `Uint8Array`, `Map`, `Symbol`, `console`, `process`, `globalThis` and
  `performance`.
- **Record and enum names** follow the same rule, and also cannot be a TypeScript built-in type
  name (`any`, `bigint`, `boolean`, `never`, `number`, `object`, `string`, `symbol`, `unknown`) or
  `as`, `infer`, `keyof`, `readonly` or `unique`.
- **Record field names** can be anything Rust allows, keywords included (`r#type` becomes `type`),
  except `__proto__`.

The fix is to rename it in Rust. There is no attribute that gives a function a different
TypeScript name.

## Leaving Beta

The feature stays Beta until **both** of these hold:

1. Bun's documentation drops the experimental, "Do not rely on it in production" status of
   `bun:ffi`, in a Bun release knext supports; and
2. knext's own checks pass on that release: loading the library on the Alpine image for x64 and
   arm64, and an end-to-end deploy of a Bun zone whose Server Action calls Rust.

Until then it is opt-in, labelled Beta in the CLI, in every generated file and on this page, and
not covered by the compatibility credential.
