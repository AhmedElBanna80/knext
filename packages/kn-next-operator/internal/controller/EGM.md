# internal/controller

## Overview
The operator's reconcilers. This package is the single source of truth for cluster state.

- `NextAppReconciler` turns a `NextApp` into a Knative Service and its owned children (ServiceAccount, Knative `caching` Image, NetworkPolicy, opt-in image-prewarm DaemonSet, retained KafkaSource, zone signing key and JWKS, and the `<app>-redis-credentials` Secret for an isolated cache). It writes one computed status.
- `BackendServiceReconciler` renders a zone function as a cluster-local h2c Knative Service with its own ServiceAccount and NetworkPolicy.
- `KnextPlatformReconciler` maintains the platform singleton's status.

A reconcile pass fetches the object, reconciles its children, computes a pure status verdict (`status_verdict.go:computeStatusVerdict`) and applies it.

## Interface

- `backendservice_controller.go:BackendServiceReconciler`: fields `Client`, `Scheme`, `APIReader` and `Recorder`. Methods are `Reconcile` and `SetupWithManager`. Also defines `BackendServiceFinalizer = "apps.kn-next.dev/backendservice-cleanup"`.

- `finalizer.go`: `ExternalCleanupFinalizer = "apps.kn-next.dev/external-cleanup"`, the `ExternalCleaner` interface (`CleanupStorage`, `CleanupCache`), and `StorageTarget` / `CacheTarget`.
- `external_cleaner.go`: `DefaultCleaner` and `NewDefaultCleaner()`. Storage cleanup uses the S3 API for providers `s3` and `minio`; any other provider is a no-op with a warning. Cache cleanup uses go-redis.
- Renderers exported for `cmd/policygen`:

## Invariants
- `nextapp_controller.go:Reconcile` validates with `validation.ValidateNextAppSpecWithBudget`, the same code the webhook uses. The reconciler is fail-closed, as defense in depth.
- New status, condition, event or requeue logic goes in `status_verdict.go:computeStatusVerdict`, which is pure with no I/O. Never add it as a new branch in `Reconcile`.
- `nextapp_controller.go:Reconcile` writes status once, and only when the computed status differs from the observed status. This prevents an idle reconcile hot-loop.
- `nextapp_controller.go:SetupWithManager` applies `GenerationChangedPredicate` (OR `rotationRequestChanged`) only to the primary `For(&NextApp{})` watch. The `Owns` watches (Knative Service, ServiceAccount, NetworkPolicy, DaemonSet) are unfiltered so drift is repaired. It also watches Revisions, DomainMappings (only when the `serving.knative.dev/v1beta1` DomainMapping kind is served), BackendServices (only when that CRD is present) and the KnextPlatform (only when that CRD is installed, which also sets `PlatformCRDPresent`).
- `setup.go:SetupControllers` always registers the NextApp reconciler, and refuses an invalid `ZoneSigningKeyConfig` before registering anything.
- `nextapp_controller.go` (step 4c): an image-prewarm DaemonSet failure degrades only `ImageCacheReady`. It never aborts the pass.
- `nextapp_controller.go` (KafkaSource step): unreachable on purpose, because `revalidationDeferred` is true for every `queue: kafka` app.
- `setup.go:SetupControllers` registers the BackendService and KnextPlatform reconcilers only when discovery reports the CRDs are installed. A discovery error other than no-match fails start-up.
- `finalizer.go`: external cleanup is best-effort and bounded by `externalCleanupTimeout = 30s`.
  - The storage scope is exactly `appStoragePrefix` (`<app.Name>/`), never bucket-wide. This must stay in step with the CLI uploader's `appKeyPrefix()`.
  - The Redis scope is `SCAN MATCH "<KeyPrefix>:*"` (the prefix glob-escaped) with batched DEL, never FLUSHDB. A cache provider other than `redis` is a no-op.
  - The legacy shared fallback prefix is never reaped (`redis_key_prefix.go:legacySharedRedisKeyPrefix`).
- `backendservice_controller.go:BackendServiceReconciler` writes only the BackendService's metadata (owner reference and finalizer), its status, and its owned children. It never writes the BackendService spec, the zone's NextApp, or the zone's Knative Service.
- `backendservice_controller.go`: a function without a two-sided binding is rendered as nothing, and anything previously rendered for it is deleted (fail closed).
- `backendservice_render.go`: function Knative Services carry `networking.knative.dev/visibility: cluster-local` and an `h2c` container port.
- `backendservice_controller.go`: a `spec.resources` quantity the render cannot parse is recorded as `functionObservation.invalidSpec` before anything is rendered. The verdict reports `Ready=False` reason `InvalidSpec` naming the field, counts it on `knext_backendservice_refusals_total`, and renders nothing; the reconcile returns no error, so it is not retried on backoff (#2423).
- `backendservice_sovereignty.go`: a function may reference only allowlisted credentials, and never a `*-knext-signing-key` Secret. The database-host check is a lint and never rejects.
- `zone_signing_key.go` rotation order:
  1. Stage a new key and publish it in the JWKS.
  2. Wait for `PropagationBound` (default 120s).
  3. Switch signing to the new key.
  4. Drop the old key after a 1h overlap.

  Key material never leaves the Secret and the derived JWKS ConfigMap.
- `zone_signing_key.go:ValidateZoneSigningKeyConfig` refuses a bound below `MinZoneKeyPropagationBound`, a negative rotation interval, and a non-zero interval that does not exceed the bound plus `ZoneKeyOverlap`.
- `redis_acl.go:appRedisCommands` must equal `MINIMAL_COMMANDS` in `scripts/redis-acl-spike.mjs` plus `client|setinfo` (`TestAppRedisCommandsMatchTheSpike`). `INFO`, `KEYS`, `FLUSHALL`, `ACL` and pub/sub are never granted.
- `redis_acl_reconcile.go:reconcileCacheCredentials`: the provisioner credential is dialled only for an endpoint registered on the KnextPlatform and equal to the app's canonical `spec.cache.url`. An isolated app fails closed (REDIS_URL points at the operator-owned Secret, which may not exist) on every refusal; it never falls back to the shared URL. The Secret is written before `ACL SETUSER`. A re-assert reuses the Secret's password only when its stored URL has the same username and canonical host; otherwise a new password is generated. The provisioner Secret must canonicalise to exactly the registered endpoint (else `ProvisionerRefused`, no dial) and is dialled at the registered form, never at the Secret's own spelling.
- `redis_acl_ownership.go`: who owns a prefix is decided by rule, never by arrival (ADR-0071 D6a rule 2). `rankedClaims` ranks EVERY NextApp on one canonical endpoint that has a prefix the operator knows, whether or not it can be issued a user: an app with `isolation: none`, or a credential in its spec, still writes under its prefix on the shared credential, so it holds the prefix without a user and anything it outranks fails closed. What an app holds is `rankingPrefix`, wider than the prefix the operator can scope a user to (`operatorRedisKeyPrefix`): a literal `REDIS_KEY_PREFIX` in `spec.env` is ranked as written; one from a Secret in `spec.secrets.envMap` is OPAQUE (the operator does not read tenants' Secrets), so the app is taken to hold any prefix: an opaque claim cannot be blocked and blocks every claim ranked after it (derived claims rank first, so they are unaffected), and a younger app behind it fails closed with `PrefixConflict` saying so. (Left out: an app with no prefix at all, the shared fallback being nobody's, and an app whose prefix is reserved, which is refused and holds nothing.) The ranking: the app whose prefix is its own derived prefix, then the oldest `creationTimestamp` (one-second resolution), then the smallest `uid`. Each claim wins unless a claim that already won overlaps it (equal, or nested at a `:`); a loser fails closed with `PrefixConflict` naming the owner and has its own ACL user removed. The owner removes the user of a visible loser, but only after `ACL GETUSER` shows the user's actual patterns overlap (the cached spec can be stale) and never a user it cannot read. A `knext-app-*` user nobody visible owns (an orphan, another cluster's) that overlaps is a `PrefixConflict` and is never deleted. The check runs again after `ACL SETUSER`, so two claimants that wrote at the same moment from different views do not both keep a user: this app's is removed and it fails closed. `reservedCachePrefix` (the platform keyspace, and the derived shape that is not the app's own, nestings included) is `validation.CacheKeyPrefixViolation`, shared with admission; a refused squat also has its earlier user removed.
- `redis_acl_reconcile.go:sharedPathLive`: `CacheCredentialsReady` says `isolation not in force: shared credential live` unless the endpoint's own state shows nothing that can reach an app's keys. The decision is per endpoint, from server state: the provisioner must not be the `default` user; every user other than the provisioner, `knext-app-*` users included, is read with `ACL GETUSER` (root patterns and selectors). An enabled user that is not `knext-app-*` whose key pattern can address a key under any app prefix on the endpoint (`patternMayCoverPrefix`, which errs toward "covers") holds the claim back; so does an enabled one, another app's `knext-app-*` user included, whose command rules (root and selectors) allow any command the SERVER lists in `@admin` or `@dangerous` (`ACL CAT admin` and `ACL CAT dangerous`, read through `RedisProvisioner.CommandCategory`; the provisioner needs `+acl|cat`), directly, through a parent (`+config`), or through any category a rule names (`+@write`, `+@keyspace`; read on demand), applied left to right (`commandCatalog.firstAllowed`), even when it holds no key pattern; an unreadable or empty answer withholds the claim; so does a key pattern over a prefix an app sets through `spec.env`, and any key pattern at all while an app on the endpoint has its prefix in a Secret; so does a same-endpoint app with `isolation: none` or a credential in its spec; a failed read is never a claim; then the two probes (no credential, `AUTH default` with an unissued password) must both be refused. The probes are necessary and not sufficient: under `requirepass` both are refused while the shared password still holds every key. No condition, event or message may say the app is isolated before that.
- `nextapp_controller.go:Reconcile`: a `reconcileCacheCredentials` error is not returned. `transientCacheCredentials` turns it into a fail-closed `ProvisionerRefused` state and `computeStatusVerdict` reports it and owns the requeue (`cacheResyncInterval` while ready, `cacheRetryInterval` for `ProvisionerRefused`, `AclUnsupported` and `PrefixConflict`), so a `Provisioned` condition from an earlier pass cannot outlive a pass that could not confirm it. `reconcile_fatality_guard_test.go` lists the step on its non-fatal allowlist for that reason.
- `redis_acl_reconcile.go:writeCredentialsSecret` is the only writer of `<app>-redis-credentials`: create with the NextApp as controller, or update. Never patch or delete; the owner reference collects it. A Secret of that name the NextApp does not control is never written.
- `finalizer.go:cleanupExternalState`: an app that has a `<app>-redis-credentials` Secret it controls takes `redis_acl_cleanup.go:cleanupIsolatedCache`; any other app takes `cleanupPlainCache` with the credential in `spec.cache.url`. The Secret decides, never `status.cache`, which is cleared on every pass that is not ready. In order: when the app owns its prefix (`ownsPrefixForCleanup`: not reserved, not outranked by any app on the endpoint that holds an overlapping prefix, whatever either app's isolation setting) and `prefixConflict` finds no other `knext-app-*` user over the same keys (an orphan, another cluster's user, a leftover of an opted-out app; users not named `knext-app-*` are not checked here), re-assert its ACL user from the Secret (a Redis restart may have lost it) and sweep as the app's own user; then `ACL DELUSER`, whatever else failed. A losing app is neither given a user nor allowed to sweep. When the endpoint is no longer registered there is no server to ask, so the sweep still runs with the app's own existing credential and the returned error names the ACL user left behind. `cleanupPlainCache` never sweeps a reserved prefix, and on a registered endpoint applies the same ownership rule: an app refused for copying an older app's prefix has no Secret, so it lands on this path, and on an open Redis its `spec.cache.url` would reap the original's keys.
- `redis_acl_cleanup.go:transientCleanupError`: a failure of the cluster's OWN API (a timeout, a 503, a refused connection) while the finalizer decides what to clean up is returned out of `cleanupExternalState`, so the finalizer runs again; it is the one cleanup failure that is not logged and dropped, because removing the finalizer needs the same API and dropping it leaks the app's ACL user. A permanent error (Forbidden, a missing kind) and any Redis failure still fail open with a Warning.
- `redis_acl_reconcile.go:parseACLGetUser` fails closed: a reply with no flags list, no keys or no commands (or a selector without them) is an error, never an empty user, which would read as "disabled, no keys". `cacheStatusFor` sets `status.cache.isolation` to `acl` only for reason `Provisioned` and to `acl-pending` while the shared credential is live, so the field makes no claim the condition does not.
- `zone_signing_key_reconcile.go`: the signing-key Secret and JWKS ConfigMap get a controller owner reference to the zone's NextApp at create only, so they are garbage-collected with it and the operator needs no delete on Secrets.
- `backendservice_controller.go:functionNetworkPolicyEnabled`: a function's NetworkPolicy is default-on and is skipped only on an explicit `spec.security.networkPolicy: false`. `RenderFunctionObjects` follows the same rule.
- `pod_hardening.go:nextAppRunAsNonRoot`: `runAsNonRoot` is rendered unless `spec.security.runAsNonRoot` is explicitly false.
- `platform_controller.go:KnextPlatformReconciler` writes only the KnextPlatform status subresource.
- `platform_rollout.go:rolloutLimiter` hands out re-render slots spaced `60/maxAppsPerMinute` seconds apart. Idle time does not bank capacity.
- `platform_rollout.go:rolloutLimiter` frees a reservation in three ways:
  - the app returns at or after its slot (`reserve`);
  - the app stops being queued without returning, and `release` drops its slot and refreshes the `rollout_pending` gauge: `NextAppReconciler.Reconcile` (`nextapp_controller.go`) calls it when the app is gone or being deleted, and when the pass is held for another reason; `gateRollout` (`platform_state.go`) calls it on any other pass that is not `holdRolloutPending`, such as the app's own spec change or an app already rendered. An error keeps the slot;
  - the reservation is more than `staleReservationAfter` (10 minutes) past its slot. The sweep runs inside `reserve`, so a stale entry keeps the gauge raised until the next `reserve` call, or a `release` for that app.
- `platform_rollout.go:rolloutLimiter` state is in memory only, and that is deliberate. A leader failover or restart starts with an empty limiter against the same cluster, and the documented behaviour is pinned by `platform_rollout_failover_test.go`:
  - The queue is rebuilt from the cluster. Progress lives in `status.platform` on each NextApp, so `NextAppReconciler.decideRollout` (`platform_state.go`) re-queues exactly the apps not yet rendered.
  - No app renders twice. A rendered app matches its applied hash and is not re-admitted. A leader that died between the Knative Service write and the status write re-applies an identical Service, which is a no-op (no second revision).
  - The cap is exceeded by at most ONE render per failover, once the old leader has stopped: the new limiter's first slot is free, so a minute holds at most `maxAppsPerMinute+1` renders, and two failovers in one minute `maxAppsPerMinute+2`. With the old leader still pacing, only "each app renders once" and "at most 2*maxAppsPerMinute+2" are pinned. Do not add persistence for this without a measured driver; failing toward progress is the chosen trade.
- `pod_hardening.go:restrictedContainerSecurityContext` is set at container level, never pod level. It sets `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, `seccompProfile: RuntimeDefault` and `runAsNonRoot: true` (unless opted out).
- `nextapp_networkpolicy.go:appMetricsPort = 9464` is the only app metrics port the default NetworkPolicy admits.

## Side Effects
- Kubernetes writes are made with `controllerutil.CreateOrUpdate`, `Patch`, `Delete` and `Status().Update`. The kubebuilder RBAC markers grant:
  - Knative serving `services` (full CRUD);
  - `serviceaccounts`, `networkpolicies`, `apps/daemonsets`, `caching.internal.knative.dev/images` and `sources.knative.dev/kafkasources`;
  - Secrets and ConfigMaps limited to `get;create;update` (zone key) or `get`;
  - `events` (`create;patch`);
  - core `namespaces` (`get`), for the cluster identity read from the `kube-system` Namespace UID;
  - NextApp, BackendService and KnextPlatform status, the NextApp and BackendService `finalizers` subresources, `nextapps` (full CRUD), `backendservices` (no create) and `knextplatforms` (`get;list;watch`).
- Read-only access to Knative `revisions`, `routes` and `domainmappings`, core `services`, `persistentvolumeclaims` and `apps/deployments`.
- `external_cleaner.go:DefaultCleaner` calls S3-compatible ListObjectsV2 and DeleteObjects (batches of 1000), and Redis SCAN and DEL, against external stores during NextApp deletion.
- Emits Kubernetes Events through `nextapp-controller` and `backendservice-controller`.
- Prometheus metrics on `metrics.Registry`:
  - from `metrics.go`: `knext_nextapp_reconcile_total`, `knext_nextapp_reconcile_errors_total`, `knext_nextapp_reconcile_duration_seconds`, `knext_nextapp_image_prewarm_errors_total`, `knext_platform_apps_held`, `knext_platform_holds_total`, `knext_platform_rollout_pending` and `knext_platform_rollout_wait_seconds`;
  - from `backendservice_metrics.go`: `knext_backendservice_reconcile_total`, `knext_backendservice_refusals_total` and `knext_backendservice_secrets_unverified_since_timestamp_seconds`.
- Generates Ed25519 keypairs (`zone_signing_key.go`) and stores them in the `<zone>-knext-signing-key` Secret. The public halves go in the `<zone>-knext-jwks` ConfigMap.
