# bench-cold-start-phases

## Overview
This directory measures the per-phase cold start of a Knative Service on any cluster. `cold-cycle.mjs` runs inside a harness pod and records one cold cycle. `drive.py` runs on a workstation and wakes the arms in an interleaved order. `analyze.py` and `stats.py` turn the resulting JSONL into phase tables and two-sample tests. The other `*-analyze.py`, `*-incluster.py` and `*-drive.py` files are study-specific drivers and analyzers. Cluster-specific settings resolve through `benchconfig.py`. The human guide is the README.md beside this file. The YAML files are cluster-specific example manifests. `kind/phase-harness-kind.yaml` is the single-node kind variant of the harness, clock and agent pods plus an additive NetworkPolicy that lets them probe the app pod past the operator's default policy; `analyze.py` takes `--p95` (adds a p95 column) and `--no-marker` for apps other than file-manager.

## Interface
- `cold-cycle.mjs <ksvc>` (and `--print-config`): one cold cycle, printed as one JSON object of `t_*` milliseconds since the request. Internal functions: `agentPodFor`, `agentIp`, `agentPoll`, `apiGet`, `watch`, `execHeal`, `clockOffset`, `tcpPoll`, `qpProbePoll`, `main`. It reads `NS` (default: the pod's service-account namespace), `AGENT_PODS`, `AGENT_LABEL` (default `app=phase-agent`), `HEALTH_PATH` (default `/api/health`), `HEAL` and `HEAL_BIN` (default `node`) from the environment.
- `drive.py <rounds> <arm1,arm2,...> <out.jsonl>` (an arm may be written `arm@pool`; the output is appended). Flags: `--dns`, `--heal ARM`, `--config`, `--context`, `--namespace`, `--pod`, `--container`, `--scratch-dir`, `--agent-pods`, `--agent-label`, `--pool-label`, `--place-mode {all,restore}` (default `all`), `--block`, `--expect-state`, `--lock-file`, `--abort-on-foreign`, `--abort-failed-fraction`, `--settle` (10), `--poll-interval` (3). Functions: `wake`, `wait_zero`, `install_harness`, `place`, `set_cordon`, `take_lock`, `restore_begin`, `check_unchanged`, `main`.
- Ready window: `cold-cycle.mjs` waits `READY_WINDOW_MS` (default 1500) after the response so late status updates, including the pod Ready condition, are recorded; `drive.py` forwards its own `READY_WINDOW_MS` environment variable to the harness pod when set.
- `kind/arms.sh [<set>|<arm>,<arm>,...]`, `kind/arms.sh --min-n [<set>]` and `kind/arms.sh --default-n [<set>]`: the arm resolver for the manually triggered native amd64 workflow `.github/workflows/coldstart-phases-kind-native.yml` (a run of this harness on a kind node). With no argument it resolves the `default` set. Without `--min-n` or `--default-n` it prints one line per arm, in the order given, and exits 2 on an unknown or duplicate arm. The ten arms are `node-1000m` (node, 1000m), `node-2000m` (node, 2000m), `node-4000m` (node, 4000m), `node-nolimit` (node, 64 CPUs), `bun-1000m` (bun, 1000m) and `bun-nolimit` (bun, 64 CPUs), which print three columns, `<arm> <runtime> <cpu-limit>` (the workflow reads a missing build as turbopack and a missing app as the spike zone), and the four build-tool arms `node-turbopack-1000m`, `bun-turbopack-1000m`, `node-vinext-1000m` and `bun-vinext-1000m` (each 1000m, on the scaffold app), which print five columns, `<arm> <runtime> <cpu-limit> <build> <app>`. The `nolimit` arms use a 64-CPU limit, above any runner, so the CFS quota never binds.
  - Sets: a bare set name is accepted as the first argument and expands to its arm list. `default` = node-1000m, node-nolimit, bun-1000m. `ladder` = node-1000m, node-2000m, node-4000m, node-nolimit. `bun` = bun-1000m, bun-nolimit, node-1000m (control). `smoke` = node-1000m only. `buildtool` = node-turbopack-1000m, bun-turbopack-1000m, node-vinext-1000m, bun-vinext-1000m; its lines carry two more columns, `<build> <app>` (the arms before it print three), and `bench/run-coldstart-native-buildtool` runs it. `kind/record-evidence.sh`, `kind/verify-bytecode.mjs` and `check-runtime.sh`'s `bun-exec` mode (vinext+bun's process is `/app/server`) back the per-arm `evidence-<arm>.json`; all are guarded by `tests/coldstart-phases-kind-native-workflow.test.ts`.
  - `--min-n <set>` and `--default-n <set>` print the set's N floor and default. An unknown set name exits 2 with these flags. An unknown bare name exits 2 as an unknown arm. The workflow's Validate inputs step refuses an `arms` input that names a set, because `arms.sh` itself accepts a set name as its argument.
- Workflow selection of the set: a push to one of five exact branch names selects it. `bench/run-coldstart-native` runs `default`, `bench/run-coldstart-native-ladder` runs `ladder`, `bench/run-coldstart-native-bun` runs `bun`, and `bench/run-coldstart-native-smoke` runs `smoke`, and `bench/run-coldstart-native-buildtool` runs `buildtool`. There is no wildcard. A push carries no dispatch inputs, so the set's default N and `ready_window_s` 20 apply. A `workflow_dispatch` `set` input (default `default`) selects the set too, and on dispatch it takes precedence over the branch name. The other dispatch inputs are `n`, `ready_window_s`, and `arms`, which is allowed only with `set=default`.
- `summarize-native.py run.jsonl [arm,...]`: prints per arm the wakes, valid wakes, wakes with `cond_Ready`, wakes with a `Pulling` event and the first-byte median and max, and exits 1 when a requested arm has no rows. `arms.sh` and `summarize-native.py` are both guarded by `tests/coldstart-phases-kind-native-workflow.test.ts`.
- `kind/check-runtime.sh <node|bun|bun-exec> [--allow-empty] < argv`: reads NUL-separated argv (the `/proc/<pid>/cmdline` format) and exits 0 only when the basename of argv[0] is the runtime, so `node /app/bundle.js` is node and `/usr/bin/bun` is not; exit 1 on a mismatch, exit 2 on an unknown runtime. `bun-exec` is the vinext+bun image, whose process is the compiled single executable `/app/server` (the image CMD, deliberately not named after a runtime): it accepts only basename `server`. `kind/run-budget.sh <n> <arms> <ready_window_s> [timeout_min post_min setup_min]`: exits 1 and prints the arithmetic when `n x arms x (45 s + window) + setup` exceeds the job timeout minus the post-step margin; the 45 s per wake and the 25 min setup are estimates.
- `kind/record-evidence.sh <arm> <runtime> <build> <app> <image> <build-log> <out-dir> <kind-node> <kind-node-pid>`: for one arm, checks the live process on the kind node (`docker exec <kind-node> cat|readlink /proc/...`) and then the pushed image (`docker pull`, `create`, `cp`, `inspect`), and writes `<out-dir>/evidence-<arm>.json` (`arm`, `runtime`, `build_target`, `app`, `image`, `bytecode`). `<kind-node-pid>` is the pid in the kind node's pid namespace (what `crictl inspect` reports) of the arm's main process. Exit 0 evidence written; 1 the proof is absent or wrong (nothing written); 2 bad arguments or setup (a missing, extra or empty argument, an unknown runtime or build, a non-numeric pid, or a vinext+bun arm with no `BYTECODE_BASELINE`, checked before any read). The workflow runs it for every arm of every set, the pre-existing ones included, immediately after the process check and before `drive.py`, and a failure fails the job; the `spec.build`/`spec.runtime` checks run before the pod and pid lookup (the spec does not change, so this costs the race nothing). Order: every live `/proc` read happens first, before the image pull, the copies and the bytecode scan, because the pod lives only about 40 s after Ready; a `/proc` read that fails, a supervisor that is alive with an empty children list (the server exited or is draining), an unreadable child, a child whose `/proc/<child>/stat` cannot be read or parsed, and a zombie child (state `Z` or `X`, read after the last `)`: a zombie keeps its `comm`, so a comm match is the one that could wrongly accept a dead child, while its exe link is unreadable and its `/proc` environ reads empty) all fail with "pod scaled away before the live check". The stat rule applies to every child of both the node and the bun loops, whatever it matched on, and to the vinext+node main process, and it is an allowlist: only `R S D T t W I P` count as live, `Z` and `X` count as exited, and an empty state (a stat ending in `) `), an unreadable stat or any other letter is treated as unreadable (the script fails closed). Every failed read appends its own docker stderr, labelled with the command (`[cat /proc/4300/environ] ...`), so the read that failed is quoted even when later reads succeed, and a wrong node name or a daemon error stays visible. "fell back" is reserved for the case where every child was read, none is a zombie, and none is the compiled executable. Children are read from `/proc/<pid>/task/<pid>/children`, the main thread's list: this assumes the supervisor spawns from its main thread (node and bun do) and needs `CONFIG_PROC_CHILDREN`. Node, turbopack: a child of the supervisor (the Next server) must have `NODE_COMPILE_CACHE` equal to the cache directory in `/proc/<child>/environ`; the supervisor's own environment is not checked. Node, vinext: the single process's `/proc/<pid>/environ`. In both, the cache directory (`/app/.next/standalone/.next/compile-cache` for turbopack, `/app/.compile-cache` for vinext) is copied out of the image and must hold at least 262144 bytes (turbopack) or 65536 bytes (vinext), the Dockerfile bake floors, and the image's `NODE_COMPILE_CACHE` must equal it; the `compile cache baked:` line of the build log is quoted. Bun, turbopack: a child of the live supervisor must be the compiled executable `/app/.next/standalone/knext-standalone-exec`, matched on the argv[0] basename, or the basename of the `/proc/<child>/exe` link, or `comm` (truncated to 15 characters by the kernel), because Next sets `process.title`, which can rewrite the cmdline; the evidence records which matched (`live_child_matched_by`: `argv0`, `exe` or `comm`) with the three values seen. The executable is copied out of the image and checked with `verify-bytecode.mjs standalone`, and the image's `STANDALONE_SERVER_EXEC` must equal that path, otherwise the supervisor would fall back to an uncompiled `bun server.js`. Bun, vinext: `/app/server` is copied out and checked with `verify-bytecode.mjs pragma` against the probe named by `BYTECODE_BASELINE`, which is required (a missing one fails); nothing live is read there (the workflow checks the process is `/app/server`). The workflow compiles that probe once, only when a bun+vinext arm is present, with `bun build --compile --minify --target=bun-linux-x64-musl` and no `--bytecode`.
  - Evidence fields: top level `arm`, `runtime`, `build_target`, `app`, `image`, `bytecode`, plus, added by the workflow, `spec_build`, `spec_runtime`, `cpu_limit` and `versions` (`next`, `react`, `react-dom`). `bytecode.kind` is `v8-compile-cache` (node) or `bun-bytecode` (bun). Node adds `cache_dir`, `bytes`, `files`, `floor`, `env_NODE_COMPILE_CACHE` (the image's), `bake_line`, and the live fields `live_pid` (the kind-node pid whose environ was read: the supervisor's Next child for turbopack, the main process for vinext), `live_via` (`supervisor-child` or `main-process`) and `live_env_NODE_COMPILE_CACHE` (the value read from `/proc/<live_pid>/environ`). Bun adds `binary`, `size_bytes`, `method` (`marker` or `pragma-differential`), `verdict`; bun turbopack also `server_exec_env` (the image's `STANDALONE_SERVER_EXEC`) and the live child's `live_child_pid`, `live_child_argv0`, `live_child_exe` (the `/proc/<child>/exe` link target, empty if unreadable), `live_child_comm` (the kernel `comm`, at most 15 characters) and `live_child_matched_by`; bun vinext has no live fields.
- `kind/verify-bytecode.mjs standalone <binary>` | `pragma <binary> <baseline-binary>`: exit 0 verified (one verdict line on stdout), 1 not verified (reason on stderr), 2 usage or unreadable input, which includes a missing baseline. `standalone` reads the `knext-standalone-exec:<24 hex>` marker out of the binary and runs `verifyBytecodeExec` (marker under a `// @bun @bytecode` pragma plus a constant-pool copy). `pragma` passes when the count of `// @bun @bytecode @bun-cjs` (Latin-1 and UTF-16LE) in the binary exceeds the count in the baseline; the verdict says "the build requested bytecode (pragma differential)", because the vinext+bun executable carries no marker and `knext build` runs no bytecode check on it, so this is weaker than the marker proof and does not show the bytecode is in the binary.
- `kind/check-versions.sh <out-dir>`: reads the `evidence-*.json` of the scaffold arms and exits 1 if `next` differs across them, a version is missing, or `react` or `react-dom` differs among the arms of one build tool; exit 2 on a missing directory. `react` and `react-dom` may differ between build tools (the vinext scaffold pins a newer range than the turbopack one): that is recorded as a `NOTE:` line, not failed.
- Native workflow caveats: `n` is 12-30 for every set except `smoke`, which allows 1-30 and defaults to 1. The N floor and default come from the set alone, never from the arm list. `ready_window_s` is 16-45 seconds. Both are checked in the workflow's Validate inputs step, and the run must also pass `run-budget.sh`. Budget example: the ladder at N=20 with a 20 s window needs 4 x 20 x (45 + 20) s + 25 min = 6700 s, which fits the 8100 s budget (the 150 min timeout less the 15 min post-step margin); that is 4 x 20 x 65 s + 25 min ≤ 135 min. The deploy step fails the job if, for any arm of any set: a bun arm's container command or main process (read from the kind node, newest Running non-terminating pod) is not bun, or a node arm's is not node; a vinext+bun arm's main process is not `/app/server` (`bun-exec`); the NextApp's `spec.build` is not the arm's build tool (absent means turbopack), or `spec.runtime` is not its runtime (checked except for vinext, where the CLI omits it); `record-evidence.sh` fails (below, including a pod that scaled away before its live check); or `check-versions.sh` fails. Within a round `drive.py` waits for zero pods before the round, then wakes the arms serially, so the previous arm's pod is still warm (and its Ready-window watch still running) while the next arm wakes; a longer `ready_window_s` lengthens that overlap. The rotation of the arm order each round spreads it evenly across arms, which mitigates it but does not remove it.
- `benchconfig.py`: `load_file`, `resolve`. The precedence is CLI flag, then `KNEXT_BENCH_*` environment variable, then config file (`--config` or `KNEXT_BENCH_CONFIG`), then default. `PHASE_POD` is still read as a legacy name for the harness pod. `bench-config.example.json` is a sample config file.
- `analyze.py run.jsonl [--no-marker] [--p95] [--by-node] [--by-treatment] [--rows] [--activator=] [--autoscaler=] [--namespace=] [--config=]`: `milestones`, `table`, `load_cp`, `probes_missing_everywhere`, `is_excluded`, `preflight`, `refuse`, `main`. Exits 2 with a stderr message on the preflight refusals (see Invariants).
- `stats.py run.jsonl <metric> <groupA> <groupB>`: `u_stat`, `exact_p` (exact Mann-Whitney), `boot_ci` (bootstrap CI), `compare`.
- Study drivers: `baseline-stability-drive.py`, `bunexec-ab-incluster.py`, `burst-ab-incluster.py`, `prepull-ab-incluster.py`.
- Study analyzers: `baseline-stability-analyze.py`, `bunexec-ab-analyze.py`, `burst-ab-analyze.py`, `cpu-boost-analyze.py`, `node-diagnosis-analyze.py`, `prepull-ab-analyze.py`.
- `prewake-ab.sh --context <ctx> [--allow-non-kind] [--namespace] [--ksvc] [--rounds] [--leads ms,...] [--minscale-leads ms,...] [--out] [--setup] [--image] [--boot-delay-ms] [--zero-timeout] [--settle] [--dry-run]`: relative A/B of cold-start latency with and without a pre-wake GET sent a fixed lead before the request (ADR-0073). Arms `cold`, `get@<ms>` (a plain GET through the activator from the client pod; the default) and, only with `--minscale-leads`, the secondary `minscale@<ms>`, interleaved and rotated per round; appends one JSON line per cycle and prints medians and ranges with deltas relative to `cold`, labelling an arm whose range overlaps cold "not distinguishable from cold". The founder's OKE procedure is `docs/benchmarks/prewake-ab-oke-runbook.md`. The summary table is printed by `prewake-ab-summary.py <jsonl>` (stdlib only, run as `python3 -I`).
- Other tools:
  - `compact.py in.jsonl out.jsonl`: trims harness JSONL for committing.
  - `readiness-probe-summary.py phases.jsonl events.json [events.json ...]`: per arm, first byte and pod Ready (median, p95, max, Ready seen), and failed readiness probes counted up to Ready, for a readiness-probe A/B (stdlib only, run as `python3 -I`). The events files are `kubectl get events --watch --output-watch-events -o json` streams and/or an events List snapshot; they supply the kubelet `Unhealthy` events with their `count`, which `cold-cycle.mjs` does not keep. The failure count is a lower bound (1 s event stamps; an event that straddles Ready counts once). Guarded by `tests/readiness-probe-summary.test.ts`; the study is `docs/benchmarks/readiness-probe-lever-2026-11-21.md`.
  - `dns-probe.js`: times resolver lookups inside an app container and prints JSON.
  - `kubelet-snapshot.sh [context] [outdir]`: saves each node's kubelet `configz` and `metrics`.
- Subdirectories: [ceiling](./ceiling/EGM.md) (patched-kubelet ceiling test) and [gke](./gke/EGM.md) (GKE runtime and minimisation tools, including [gke/variants](./gke/variants/EGM.md)), and `kind/` (no EGM of its own; it holds `phase-harness-kind.yaml`, the single-node kind harness manifest for the clock and agent pods, plus the harness-only NetworkPolicy allow `bench-harness-probes`, which is needed because the operator's default policy blocks direct probes).

## Invariants
- `analyze.py` preflight, run after the error/code/marker filter on the VALID rows the tables are built from, so a probe-bearing row the filter drops does not count. Empty input exits 0. Non-empty input with zero valid rows exits 2: "every row errored" when all rows carry `error` (the wakes failed, not the probes), otherwise "no valid rows". Valid rows where every row lacks every probe milestone (`PROBE_KEYS`: `qp_probe_ok`, `app_tcp_3000`, `same_node_tcp_3000`, `same_node_health_ok`, null or absent) exit 2 with a stderr message: the probes never reached the pod, typically a NetworkPolicy dropping them. Without the check, the tables silently fall back to `min(cond_Ready, first_byte)`. Partial nulls are allowed. Mutation-proved 2026-11-20 (PR #229): moving the check back before the filter (`preflight(raw, raw)`) made `tests/bench-analyze-preflight.test.ts` exit 1 with three failing tests.
- `benchconfig.load_file`: an unknown config key (other than `$comment`) raises `SystemExit`, so a typo cannot fall back to a default silently.
- `cold-cycle.mjs` throws if the arm does not have zero pods at the start (`${ARM} has N pod(s); not at zero`) and if no namespace can be found. Apart from `HEAL=1`, which execs one DNS lookup in the new container, it is read-only against the cluster (header comment).
- `drive.py`: each round waits for every arm to reach zero pods and then rotates the wake order. `wake` starts the harness detached and guarded by `[ -e out ]`, so it never starts a second run. `take_lock` takes a non-blocking `fcntl.flock` and exits if another restore-mode driver holds the lock, so only one runs per workstation. `check_unchanged` stops the run if someone else changed a cordon this run manages.
- `kubelet-snapshot.sh` requires a context (argument or `KNEXT_BENCH_CONTEXT`). Without one it exits 2.
- `prewake-ab-summary.py`: a cycle whose `status` is not `"200"` is excluded before the medians, ranges and verdicts are computed, and the count is printed as `non-200 cycles excluded: N` when N is non-zero. It exits if the cold arm has no 200 cycle. A run that prints the exclusion line must report N with its table (see ADR-0073, "Kind-relative evidence").
- `prewake-ab.sh` exits 2 on a context not starting with `kind-` unless `--allow-non-kind` is given, on `--setup` with a non-kind context, and on an `--image` not pinned by digest. `--dry-run` makes no `kubectl` call. Its EXIT trap removes the min-scale annotation if a cycle aborts while it is set and restores the grace period `--setup` changed.

## Side Effects
- `drive.py`: `kubectl cp` and `kubectl exec` into the harness pod. In placement modes it also runs `kubectl cordon` and `uncordon` (`set_cordon`). It writes the output JSONL.
- `burst-ab-incluster.py` and `prepull-ab-incluster.py`: `kubectl apply --validate=strict`, `kubectl patch nextapp ... --type merge`, and (prepull only) `kubectl create` of pull pods. `prepull-ab-incluster.py` also pushes images with `crane append` and `crane export`.
- `cold-cycle.mjs`: Kubernetes API GET and watch calls using the pod's service-account token. Also TCP connects and `K-Network-Probe: queue` probes to the new pod, and agent polls.
- `prewake-ab.sh`: the default `get@` arm only runs `kubectl exec` into the client pod (no cluster write). Per `minscale@` cycle (opt-in), `kubectl annotate podautoscaler <revision> autoscaling.knative.dev/min-scale=1` and its removal (a Knative-internal object; a measurement knob, not a product surface), plus the same exec. `--setup` (kind only) applies a namespace, a target ksvc and a client pod, and patches `config-autoscaler` `scale-to-zero-grace-period` to `10s`, restoring the prior value on exit. Appends to `--out`.
- `kubelet-snapshot.sh`: read-only `kubectl get --raw` calls through the node proxy. It writes files under the outdir (default `$TMPDIR/kubelet-snapshot`).
- The analyzers read JSONL and print. Some write `--json` output.
